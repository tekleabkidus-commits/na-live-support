**Product:** AI-First Support Platform for Betting Companies **Document series:** 16 of 19 · Standalone enterprise specification **Audience:** Backend engineers, frontend engineers, designers, QA, product, operator admins, platform owner **Depends on:** Doc 01 (settings engine T-04, tenancy, i18n plumbing, feature-flag registry FR-11), Doc 02 (auth screens theming, email deliverability), Doc 03 (permissions settings.*, branding.edit, features.toggle, languages.manage), Doc 09 (persona identity slots), Doc 13 (widget theming reuse of the validator). ## 1. Executive Summary

This document specifies the three subsystems that make the platform an operator’s own product rather than a vendor’s tool: (1) the **White-Label system** — a versioned theme layer (names, logos, favicon, colors with enforced contrast validation, fonts, login page, email and notification templates, chat-widget branding hand-off, AI-assistant identity hand-off, copyright/footer/legal links, sender identities) with draft → preview → publish → instant rollback, applied at runtime so one deployment serves every brand with **nothing hardcoded** — a claim enforced by a CI string-lint build gate; (2) the **Settings system** — the operator-facing surface of Doc 01’s settings engine, organized into a coherent Backoffice (business hours source links, languages, timezones, file limits, session/password policy, notification preferences with per-user and role-default layers, SLA/auto-close cross-links, and the full registry of every *. key the other 18 documents declared), each setting typed, validated, provenance-stamped, and audited; and (3) **Feature Flags** — the Pennant-backed per-tenant module switches (Telegram, Live Chat, SMS, AI Chatbot, AI Copilot, KB, Reports, Surveys, File Uploads, Voice, Translation, SLA, Automation, and every flag other documents registered) with dependency awareness, blast-radius confirmation, and no-deploy toggling. It also specifies the **translation manager** for operator-editable UI strings and customer-facing template text, and the **notification preference model** that Docs 06/07/12/15 route deliveries through. Everything here is configuration-as-data with the platform’s standard honesty: previewed before published, versioned after, audited forever.

## 2. Purpose

- Deliver the master requirement “no code changes for branding, permissions, channels, AI behavior, workflows, forms, notifications, or settings” as concrete, testable mechanics.

- Consolidate every settings key the series declared into one navigable, safe Backoffice rather than nineteen scattered screens.

- Make flags honest: a module off is *off* (navigation, permissions surfaces, API, jobs) with dependencies handled, not a hidden menu item.

## 4. Functional Requirements

### 4.1 Theme model & brandable inventory

FR-01 Theme = versioned JSON {company_name, product_name, logos (light/dark, constraints validated: SVG/PNG, ≤ 512 KB, aspect guidance), favicon set (generated from one upload), color tokens (primary, accent, surface adjustments — validated per FR-04), font selection (curated set incl. Inter, Noto Sans Ethiopic; custom font upload deferred §19), login page (background image/color, welcome copy per language), email header/footer (logo, address block, legal footer per language), copyright line, footer links (label+URL pairs, per language), sender identities (email from-name + from-address per purpose: auth, notifications, reports — domain status read from Doc 18), AI assistant identity slots (name/avatar — content edited in Doc 09’s persona screen, referenced here for inventory completeness), widget brand token hand-off (Doc 13 reads the same token set)}. FR-02 Brandable-surface inventory (normative checklist, each themed surface listed with its consuming doc): staff app chrome + login (Doc 02), emails (Doc 02 auth, Doc 12/15 schedules, Doc 16 notifications), chat widget (Doc 13), Telegram persona surfaces (Doc 05/09), SMS sender IDs (Doc 14 — referenced, managed there), exports/watermarks (Docs 04/15), error pages, PDF transcripts (Doc 04). The inventory page renders live thumbnails per surface from the draft theme — the preview IS the checklist. FR-03 Lifecycle: exactly one published theme per tenant + at most one draft; edit → live preview (per-surface thumbnails + full-app preview mode banner “PREVIEWING DRAFT — visible only to you”) → publish (validation gate) → instant propagation (CSS-variable + config-cache swap ≤ 60 s cluster-wide) → version history with one-click rollback (rollback is a publish of a prior version — same pipeline, same audit). FR-04 Validators (publish gates): color contrast (WCAG AA pairs computed across the token matrix; failing combinations block publish with auto-suggested nearest-passing values — the Doc 13 validator is this one, shared); asset constraints (type/size/dimensions); footer-link URLs (https, no javascript:); email templates render-tested (variable resolution + client-safe HTML subset); missing-language completeness warnings (non-blocking for optional surfaces, blocking where a language is customer-enabled — Doc 12/13/14 completeness-gate family). FR-05 **Nothing-hardcoded enforcement:** the CI string-lint (Doc 01 FR-09) fails builds on user-visible literals outside the i18n/theme layer; a release-gate visual sweep renders the surface inventory under a hostile test theme (garish colors, long names, RTL strings) asserting zero unthemed remnants — the “find the hardcoded blue” test, automated.

### 4.4 Feature flags

## 6. User Stories

US-01 As an operator admin, I rebrand for a sponsorship deal — logo, colors, emails, widget, login — preview every surface, publish at midnight, and roll back in one click when marketing changes its mind at 00:15. US-02 As an operator admin, I reword the bot’s Amharic greeting and the ticket-resolved email without asking anyone technical, and both show a “modified” badge with reset available. US-03 As a platform owner onboarding tenant #12, I import the standard config bundle, review the diff, apply, and hand over a branded, configured instance the same afternoon. US-04 As a supervisor, my notification preferences let me mute bulk-completed pings but the platform honestly tells me SLA breaches are mandated for my role. US-05 As an operator admin during an incident, I flip Voice Messages off, see exactly what that touches first, and nothing breaks — it’s just gone until I bring it back. US-06 As a compliance reviewer, every branding publish, flag flip, and security-setting change has an actor, a timestamp, and old/new values in one audit trail. US-07 As a translator, the missing-strings view shows me the 14 Amharic gaps players actually hit last week, not an alphabetical wall of 10,000 keys.

## 7. Business Rules

BR-01 Nothing hardcoded is a build gate, not a guideline (FR-05): the lint + hostile-theme sweep make regressions unshippable — the master requirement’s strongest claim gets the strongest enforcement. BR-02 Accessibility outranks brand preference: the contrast validator blocks publish; the platform offers nearest-passing suggestions but never a “publish anyway” override (the one validator without an escape hatch — a deliberate stance, documented to operators). BR-03 Preview before publish, always: no theme, template, or customer-facing string change reaches customers without a rendered preview having been available (the pipeline enforces the draft stage; publishes record that preview existed). BR-04 Flags hide, never destroy: toggling off preserves all data and configuration; re-enabling restores the module as it was (parked work drains per each module’s contract). BR-05 Platform minimums are floors (Doc 02 BR-05 family): security settings render their locked floors visibly; white-label extends to identity, never to weakening the platform’s safety or the AI disclosure (Doc 09 BR-05 cross-referenced on the branding screen where the assistant identity is edited). BR-06 Mandated notifications are honest (FR-09): a locked row says who mandated it and why — silent force-delivery and silent suppression are both prohibited. BR-07 Config import never merges silently: every applied key is an individual, previewed, audited change (FR-13) — bulk convenience without bulk opacity.

## 11. Security Requirements

SEC-02 Footer/legal link URLs validated (https, domain-visible in the editor); email templates restricted to the safe HTML subset (no scripts/forms; link targets rendered visibly in preview) — brand surfaces cannot become phishing surfaces. ## 15. Edge Cases

EC-01 Theme published while an agent mid-session → CSS vars swap live (no reload); in-flight modals keep functioning (tokens only change values); the visual sweep includes a mid-interaction snapshot. EC-02 Rollback to a version referencing a since-deleted asset → publish gate re-validates assets; missing assets block with a re-upload prompt (versions pin asset URLs, but deletion via retention is possible — Doc 10 EC-05 family). EC-03 A translation override for a key later removed by a platform release → orphaned overrides listed in a maintenance view (never rendered, never silently deleted; operator cleans with one click). EC-04 Role default changed while a user holds an explicit override → user override wins (the three-layer contract); the role-admin view’s affected-count excludes overriders with a note. EC-05 A mandated category the user’s channel can’t deliver (SMS-mandated, user has no phone) → delivery falls back in-channel-priority order (in-app always exists); the mandate means “cannot mute,” not “must SMS” — documented on the lock tooltip. EC-06 Flag off while its module’s queue holds 10k jobs → consumers pause post-in-flight; parked work per module contract; the flag card shows the parked count live; re-enable drains (BR-04 proven at scale in the drill). EC-07 Two admins editing the theme draft → single-draft model with the Doc 10 FR-05 lock pattern (soft lock + takeover, audited). EC-08 Import bundle from a newer platform version → compatibility check rejects with the version delta named; partial-schema imports are never attempted. EC-09 Contrast-passing colors that fail on a surface with an image background (login) → the login preview computes contrast against the uploaded background’s sampled regions; failures block with the overlay-scrim suggestion (the one surface needing image-aware validation). EC-10 A tenant disables its last customer-facing channel flag (Telegram + Live Chat both off) → allowed (SMS-notification-only operation is conceivable) but the confirm states the consequence plainly (“customers will have no way to contact support through the platform”). EC-11 Sender domain verification lapses (DNS change, Doc 18 detects) → affected sender identities flip to warning state; customer-facing sends fall back to the platform default sender with an alert (deliverability continuity over brand purity, stated in the warning). EC-12 Quick-mute (Doc 07) set “today” spanning midnight in the user’s local vs tenant timezone → mute windows compute in the user’s profile timezone (personal preference = personal clock; documented).

## 16. Failure Scenarios

FS-01 Theme cache loss → app shell falls back to the platform-default theme (branded-but-generic, never broken) while the cache rebuilds from DB; a banner notes degraded branding to admins only. FS-02 Email template render failure post-publish (client-quirk discovered) → per-template rollback (versioned independently within the theme’s email group); the send pipeline falls back to the plain-text alternative part (always generated) — deliveries continue, notification to admins. FS-03 Pennant/flag store unavailable → flags resolve from the last local cache (fail-static: no spontaneous module flips during the outage); toggling disabled with an honest error until recovery. FS-04 Import saga failure mid-apply → per-row results show applied/failed/not-attempted; no rollback of applied rows (each was individually valid — BR-07’s model); the results screen is the recovery worklist. FS-05 Notification gate failure → fail-open to in-app only (the always-available channel) with metric + alert; email/SMS deliveries pause rather than misroute (Doc 02 NFR-04’s fail-posture family, direction chosen per channel risk).

SS-02 The FR-05 gate catches a real regression: a PR adds a hardcoded “Submit” — CI fails with the exact file/line; the string ships as a key instead; the guarantee stays true without anyone being the hero. ## 20. Risks

R-01 Theme flexibility vs product coherence (Medium/Medium) → the token set bounds what varies (colors/assets/copy, never layout); the hostile sweep keeps every combination shippable; custom-CSS requests are the named scope wall (declined in v1, revisit only with the sweep extended). R-02 Translation-override drift from shipped intent (Medium/Low) → modified badges, reset paths, orphan maintenance, and the shipped value always visible beside the override. R-03 Flag misuse as a pseudo-permission system (Medium/Medium) → flags are tenant-wide by design; per-role visibility is Doc 03’s job — the flags screen says so where admins will look for it. R-04 Settings sprawl overwhelming operators (High likelihood, Doc 01 R-03 inherited) → the registry-driven IA with search, grouped screens, and consequence warnings is the containment; the registry sign-off gate is the prevention. R-05 Import-driven misconfiguration at scale (Low/High) → diff-preview + per-row validation + individual audits (BR-07) make imports the *safest* bulk path, not the riskiest — provided the preview habit holds (onboarding materials).

## 21. Recommendations

- Build the FR-05 enforcement pair (lint + hostile sweep) before the theme editor itself — the guarantee is worthless if even one release shipped without the gate, and retrofitting the sweep against accumulated violations is the expensive order.

- Ship the incident page (AC-10) in the same milestone as the first kill switch it hosts; scattered stop buttons are how 2 AM incidents get worse.

- Seed every new tenant from a maintained config bundle (FR-13) that the platform team dogfoods on its own staging tenant — onboarding quality then improves as a side effect of normal operations.

- Keep BR-02’s no-override contrast stance through the first operator complaint about their brand orange; the moment one inaccessible palette ships, the validator becomes advisory forever.

- Treat the notification-category registry with the same governance as metrics and permissions (the three registries are the platform’s constitution) — a module shipping notifications outside T-05’s gate reintroduces exactly the ungovernable noise this design eliminates.
