# Document 17 — Audit Logging & Compliance

**Product:** AI-First Support Platform for Betting Companies **Document series:** 17 of 19 · Standalone enterprise specification **Audience:** Backend engineers, frontend engineers, security engineers, compliance officers, QA, product, operator admins **Depends on:** Doc 01 (append-only audit table, outbox, tenancy, retention engine), Doc 02 (auth events, session identity), Doc 03 (audit.view/export high-risk permissions, high-visibility event classes, four-eyes machinery), Doc 08 (customer export/erasure initiation, RG history), every module (event emission per its SEC sections). Consumed by: security monitoring (Doc 18), regulators/auditors via exports, the QA test plans (Doc 19). **Stack context:** Laravel, PostgreSQL (append-only partitioned audit table with restricted DB grants), Redis (write batching), Horizon, Browsershot/CSV exports

## 1. Executive Summary

This document specifies the platform’s accountability layer: the **audit log** — an append-only, immutable, tenant-scoped record of every consequential action (logins, ticket changes, user and permission changes, settings and branding changes, AI configuration changes, SMS and Telegram administrative activity, customer-data operations, exports themselves) with actor, action, object, old value, new value, IP, user agent, and timestamp — its **two visibility classes** (standard and high-visibility, the Doc 03 classification realized as one pipeline with different surfacing), the **audit viewer** (filterable, expandable old→new diffs, per-object timelines embedded across the product, saved investigations), **integrity guarantees** (database-grant immutability, hash chaining per tenant-day, external anchor option), **retention and legal hold**, the **compliance workflows** built on top: customer **data export** (the subject-access package) and the **erasure workflow** (request → approval chain → staged execution across messages, media, profiles, and derived data → verification report — the wiring for Doc 06 BR-01’s reserved deletion and Doc 08 SEC-04’s initiation), **regulator-ready exports** (scoped, watermarked, tamper-evident), PII-masking rules for what the audit itself stores, and the module-by-module **coverage matrix** that CI enforces so no auditable action ships unaudited. The design stance: the audit log is the platform’s memory of record — it is written by everything, editable by nothing, and readable only with reason.

## 2. Purpose

- Provide one authoritative, immutable trail answering “who did what, when, to what, and what changed” for every consequential action across all 18 other documents.

- Make compliance operational: subject-access exports and approval-gated erasure as designed workflows, not ad-hoc engineering favors.

- Guarantee integrity in a form an external auditor or regulator can verify (immutability by construction + tamper-evidence).

## 3. Scope

**In scope:** the audit event model and write pipeline; the coverage matrix and its CI gate; visibility classes; PII rules for audit content; the audit viewer and embedded per-object timelines; search/filter/saved investigations; integrity (grants, hash chains, anchoring); retention & legal holds for audit data; audit exports; the customer data-export package; the erasure workflow end-to-end; security-monitoring feed hand-off (Doc 18); events about the audit system itself (exports, hold changes, erasures). **Out of scope:** application event production (each doc’s SEC sections own emission; this doc owns the sink, the matrix, and the gate); operational/security alerting rules (Doc 18 consumes the feed); message/media retention policies themselves (Docs 01/04 — erasure interacts with them here); the customer-facing privacy policy text (operator content, Doc 16 legal links).

## 4. Functional Requirements

### 4.1 Event model & write pipeline

FR-01 Audit entry = {id (uuidv7), tenant_id, actor {type: user|system|ai|api_key, id, display snapshot}, on_behalf_of (nullable — jobs-as-user per Doc 03 SEC-06), module, action (namespaced key from the coverage matrix, e.g. tickets.merged, auth.2fa.reset_by_admin), object {type, id, label snapshot}, secondary_objects[] (merge targets, transfer destinations), old (jsonb), new (jsonb), reason (where the emitting module requires one), visibility (standard | high), ip, user_agent, trace_id (Doc 01 T-07), occurred_at, chain fields (§4.4)}. Label snapshots make entries readable after renames/deletions (the Doc 08 tombstone philosophy applied to history). FR-02 Write path: modules emit via the Doc 01 outbox (transactional with the action) → the audit consumer writes batched inserts to the append-only table; direct synchronous writes are used only for auth events with no surrounding transaction (Doc 02’s) — both paths land in one table with one schema; write failures never fail the business action (the consumer retries from the outbox; the outbox’s at-least-once + entry idempotency on event id guarantees no gaps and no dupes). FR-03 **Coverage matrix (normative + CI-enforced):** a code-registered map of every auditable action key → {emitting module, required fields (does it need reason? old/new? secondary objects?), visibility class}. The matrix aggregates every SEC-section commitment made in Docs 02–16 (auth events; RBAC changes incl. overrides and four-eyes; ticket operations; customer identity/merge/RG/block; Telegram bot/connection admin; widget config; SMS templates/gateways/opt-outs/broadcasts; KB publish/visibility; automation/SLA/forms/fields; routing structure; report exports/schedules; branding/settings/flags/imports). CI gate: (a) every matrix key has at least one emission-path test; (b) any route/job performing a matrix-mapped mutation without emitting fails the build (static analysis on the transition/write services + runtime assertion harness) — the “no auditable action ships unaudited” claim made mechanical. FR-04 PII rules for audit content: old/new payloads store the changed fields only (never full-record dumps); message bodies never enter audit (references by id — the conversation is its own record per Doc 04); phones/emails masked per the shared scrubber (Doc 08 SEC-03) in payloads *except* where the change is the identity value itself (then stored full, since “what changed” is the point — visibility high, access gated); RG payloads store the flag state + reason, never conversation excerpts (the excerpt ref points into Doc 08’s restricted history).

### 4.2 Visibility classes & access

FR-05 standard: routine operational trail. high: the Doc 03 high-risk classes + this doc’s own sensitive actions (audit exports, hold changes, erasure steps, RG-related entries, identity-value changes, opt-in restorations, impersonation-adjacent anythings). Both classes live in one table; high additionally: fans out to the Doc 18 security feed in near-real-time, renders with the shield treatment, and its *read access* requires audit.view (standard per-object timelines are visible to users who can see the object itself — see FR-07’s duality). FR-06 Access: the full audit viewer requires audit.view (high-risk permission); audit.export separately gates exports; RG-related entries additionally require customers.rg_flag.view (double-gate — holding audit.view alone renders them elided per Doc 08 BR-03’s absence rule); reads of high-visibility entries are themselves counted (not per-row logged — a daily access-summary entry per viewer prevents infinite-regress noise while preserving “who was looking”). FR-07 Per-object timelines (the embedded surfaces): tickets (Doc 06 events feed — already specified there, sourced here), customer profiles’ Audit tab (Doc 08 §8), roles/users (Doc 03), articles (Doc 10 versions + this trail), settings rows’ provenance lines (Doc 16) — each shows that object’s standard entries to viewers with object visibility, elides high entries for non-audit.view holders (a settings row shows “changed by Hanna, Jul 12”; the security-policy change *details* need audit.view). One source, many windows.

### 4.3 Viewer, search, investigations

FR-08 Audit viewer (Backoffice → Platform → Audit Log): filter bar (date range, actor, module, action key [grouped picker], object type + id lookup, visibility class, IP, has-reason, trace_id); results as a virtualized table (time, actor, action label, object label, visibility shield); row expand = old→new diff (field-level, added/removed/changed styling per the platform diff grammar), full metadata, linked secondary objects, jump-to-object, jump-to-trace (all entries sharing the trace_id — the “everything this request touched” view). FR-09 Saved investigations: named filter sets (personal), shareable to other audit.view holders; an investigation can be exported as one package (FR-12). FR-10 Retention & holds for audit data: default retention audit.retention.months (platform floor 24, tenant-raisable); **legal hold**: scoped holds {tenant-wide | actor | object | date-range} freezing matching entries against retention (holds require audit.export-level permission + reason, are themselves high-visibility entries, and list actively on a Holds screen); retention jobs (Doc 01’s engine) skip held ranges with the pre-drop copy-out pattern (Doc 04 EC-09 family).

### 4.4 Integrity

FR-11 Immutability by construction: the application DB role holds INSERT+SELECT only on audit partitions (Doc 01’s grant posture); no UPDATE/DELETE grants exist for any application path; partition drops (retention) run under the platform maintenance role with the hold checks; migrations touching the audit table require a platform release note (change-control flag in CI). FR-12 Tamper evidence: per tenant per UTC day, entries chain: entry.chain_hash = SHA-256(prev_chain_hash ‖ canonical(entry)); the day’s final hash is sealed into a audit_day_seals row (tenant, date, final_hash, entry_count) at day close; a verify job re-walks random sampled days nightly (mismatch = Sev-1 with the exact break position); optional external anchoring (setting): daily seal hashes POSTed to an operator-designated external timestamping endpoint / write-once bucket — proving the platform itself couldn’t silently rewrite history. FR-13 Verification tooling: audit:verify {tenant} {date-range} command producing a signed verification report (used in FR-15 exports and by auditors on request); the viewer shows each day’s seal status (sealed ✓ / pending / mismatch ⚠).

### 4.5 Compliance workflows

FR-14 **Customer data export** (subject access; initiated per Doc 08 SEC-04): async job assembling {profile + identities + custom fields, conversations + messages (their own — the customer’s side and staff public replies; internal notes excluded by definition), media manifest with retrieval links (time-limited), tickets summary, CSAT responses, SMS log (to them), consent-adjacent records (opt-outs), the customer’s audit-relevant entries (actions *on* their data, actor names elided to roles for staff privacy — “an agent”, “a supervisor” + timestamps)} rendered as a structured JSON + human-readable PDF; permission customers.export; delivery to staff (who convey it) — the platform has no customer-direct delivery channel for it in v1 (documented; §19). FR-15 **Erasure workflow** (the Doc 06 BR-01 / Doc 08 reservation, now specified): request (staff-entered with source: customer request | regulator | operator policy; scope: full customer | specific conversations) → **approval chain**: requires a distinct approver holding customers.delete (four-eyes mandatory here regardless of the Doc 03 tenant setting — hard rule), with a review screen showing exactly what will be erased (counts per data class) and what will be **retained with justification** (financial-dispute records under legal retention, audit entries themselves [erasure is logged, not erased — the entry’s PII follows FR-04 masking], aggregate report contributions [already anonymous by construction]) → staged execution: messages/media purged (Doc 04 stores + derived transcripts/OCR), profile anonymized to a tombstone (erased state: display “Erased customer”, identities removed, the Doc 08 merge-pointer integrity kept via the tombstone), search/retrieval indexes purged, caches invalidated, backups handled per Doc 18’s documented backup-erasure policy (staged expiry — stated honestly in the verification report rather than pretending instant backup erasure) → **verification report**: per-class before/after counts, residuals with justifications, seal-referenced audit entries for every step; the report is the artifact handed to the requester/regulator. FR-16 Erasure interactions (normative): open tickets block full erasure (resolve/close first — listed in the review screen); legal holds block conflicting erasures (the conflict surfaces at review with the hold’s reason; resolution is a human decision between the two legal obligations, recorded); RG history follows the same erasure scope (it is the customer’s data) with its restricted-access trail noting the erasure; Doc 15 aggregates are untouched (event-sourced values already contain no identity — asserted by the Doc 15 exclusion/PII posture); the Doc 08 30-day merge snapshots covering the customer are purged with the erasure. FR-17 Audit exports: scoped {filters | investigation | object timeline | verification report} → CSV (stable action keys + localized labels, Doc 15 FR-16 pattern) and PDF (watermarked: exporting user, timestamp, filter parameters, seal-status summary); every export is itself a high-visibility entry with its parameters; regulator packages combine an export + the FR-13 verification report.

### 4.6 Events about the audit system

FR-18 audit.exported, audit.hold.created|released, audit.verify.mismatch, erasure.requested|approved|rejected|executed|verified, subject_export.generated — all high-visibility (the watchers are watched).

## 5. Non-functional Requirements

NFR-01 Audit write adds ≤ 2 ms p99 to emitting transactions (outbox insert; the consumer’s batch insert amortized ≤ 0.5 ms/entry). NFR-02 Ingest keeps up at 500 entries/s platform burst with lag alerting (Doc 01 budgets); viewer queries ≤ 800 ms p95 over 100 M entries (partition pruning + the filter indexes). NFR-03 Day-seal computation ≤ 5 min after UTC day close per tenant; nightly sampled verification ≤ 30 min platform-wide. NFR-04 Subject export assembly ≤ 10 min p95 for a 10k-message customer; erasure execution ≤ 60 min p95 same scale with per-stage progress. NFR-05 Zero-gap guarantee: for any matrix-mapped action that committed, an audit entry exists (the outbox transactionality + FR-03’s gate; asserted by the chaos suite — kill the consumer mid-burst, drain, reconcile counts exactly). NFR-06 The coverage matrix is complete by construction: a release cannot add a high-risk permission (Doc 03), a settings key (Doc 01), or a notification category (Doc 16) without a matrix mapping (the three-registries cross-check in CI — the platform’s constitution audits itself).

## 6. User Stories

US-01 As a compliance officer, I answer a regulator’s “show me every change to responsible-gaming handling this quarter” with one saved investigation and a sealed, verifiable export. US-02 As an operator admin, when a bonus was mis-credited, the ticket’s timeline plus jump-to-trace shows me the rule, the agent, and the settings change that aligned to cause it — in ten minutes. US-03 As a security engineer, high-visibility events stream to monitoring in near-real-time, and I can prove to an auditor that nobody — including us — can rewrite yesterday. US-04 As an operator, a customer invokes their erasure rights; two of my staff independently review what goes and what legally stays, it executes in stages, and I hand the customer a verification report instead of a promise. US-05 As an agent, I see honest provenance everywhere (“changed by Sara, yesterday”) without needing — or having — access to the full audit trail. US-06 As a platform engineer, I cannot ship a mutation the matrix doesn’t know about; the build tells me before review does. US-07 As a QA lead, the audit trail is my oracle: every test scenario’s expected entries are assertable fixtures (Doc 19 consumes the matrix as its checklist).

## 7. Business Rules

BR-01 Append-only means append-only: no correction mechanism exists — errors are corrected by subsequent entries referencing the erroneous one (corrects: entry_id), never by mutation; even platform staff operate under this rule (the grants make it physics, not policy). BR-02 The audit log audits itself (FR-18): exports, holds, verifications, and erasures of audited data are first-class entries — there is no meta-level exempt from the trail. BR-03 Erasure is honored and honest (FR-15): what’s erased is erased, what’s retained is justified in writing, and backup-lag reality is stated, not hidden — a verification report that admits staged backup expiry is trustworthy; one that claims instant total erasure is not. BR-04 Reads are privileged, writes are universal: every module must write; almost nobody may read broadly (the FR-06/07 duality) — provenance for all, surveillance for none. BR-05 Actor truth: system actions say system, AI actions say ai, jobs-as-user say both (actor + on_behalf_of), machine tokens say their service account (Doc 02 BR-03) — the trail never launders agency. BR-06 High-visibility is a floor, not a ceiling: modules may classify up, never down; the matrix owns the classification and change control owns the matrix. BR-07 The audit trail outlives its subjects: renames, deletions, merges, and erasures leave label snapshots and tombstone references so history stays readable (FR-01) — within FR-15’s erasure masking for the erased subject’s PII.

## 10. Technical Requirements

T-01 Storage: audit_log monthly partitions per Doc 01 (append-only grants per FR-11), indexes on (tenant, occurred_at), (tenant, actor_id, occurred_at), (tenant, module+action, occurred_at), (tenant, object_type+object_id, occurred_at), trace_id; audit_day_seals, audit_holds, erasure_requests (+stages), subject_exports. T-02 The coverage matrix as a code registry (the platform’s fourth registry, alongside permissions/settings/notifications — NFR-06’s cross-check binds all four): key metadata per FR-03; emission helpers per module consume it (an emit call with a key the matrix lacks throws in dev/CI). T-03 Write pipeline: outbox consumer with batch inserts (COPY-style bulk), entry idempotency on event id; the synchronous auth path shares the insert code; chain-hash computation is in the consumer (single-writer per tenant partition via a per-tenant queue lane — ordering for the chain without global serialization). T-04 Sealing & verification: day-close job per tenant lane; the verify command re-canonicalizes entries (stable JSON canonicalization documented and versioned — canonicalization changes require dual-hash transition releases); external anchoring driver behind a simple interface (HTTP POST / S3 object-lock write). T-05 Erasure engine: staged saga (Doc 08 T-03’s compensation pattern inverted — here stages are irreversible by design, so the saga is checkpoint-and-continue with per-stage verification counts, never rollback); purge implementations delegate to owning modules’ erasure hooks (Doc 04 message/media purge, Doc 08 profile tombstone, index purges) — each hook returns counted results the report aggregates; backup-expiry tracking reads Doc 18’s backup-generation metadata to compute the honest “fully expired by” date. T-06 Subject-export assembler: per-class collectors (same owning-module hook pattern) → JSON schema + PDF render; media links are time-limited signed URLs minted at download, not baked into the package. T-07 Elision rendering: per-action-key elision mode (acknowledge vs absence) from the matrix; the query layer applies it (RG absence at the query per Doc 08 SEC-01’s pattern — never serializer-level). T-08 Contract tests: the FR-03 CI gate pair (matrix-coverage static analysis + the runtime assertion harness running each module’s mutation fixtures and asserting exact expected entries — Doc 19’s shared oracle); chain integrity chaos (consumer kill mid-burst → NFR-05 reconciliation; deliberate tamper via superuser in a test DB → verify catches at the exact position); erasure end-to-end fixtures per data class incl. conflict cases (FR-16); elision-mode matrix per role; export watermark/parameter completeness.

## 11. Security Requirements

SEC-01 The grant posture (FR-11) is verified by a standing test that attempts UPDATE/DELETE as the app role and expects permission failure (the physics test, run per deploy). SEC-02 audit.view/audit.export are Doc 03 high-risk with the granting itself high-visibility (recursion intended); the daily access-summary (FR-06) feeds Doc 18’s anomaly rules (an admin suddenly reading months of RG-adjacent trail is a signal). SEC-03 Export packages: watermarked, parameter-stamped, checksum-listed (each file’s SHA-256 in a manifest), the manifest referenced in the export’s own audit entry — a leaked package is attributable and a modified one is detectable. SEC-04 Erasure’s mandatory four-eyes (FR-15) cannot be disabled by tenant settings (contrast with Doc 03’s optional four-eyes — deletion of people’s data is the one place the platform overrides operator convenience). SEC-05 The external-anchor credentials (T-04) are write-only from the platform’s perspective (object-lock/append endpoints) — an attacker with full platform access still can’t un-anchor sealed days. SEC-06 Trace-id joins (FR-08) respect per-entry gates — a trace view renders only the entries the viewer may see, with count-of-hidden disclosed (“3 entries not visible to you”) since trace completeness itself is investigative signal (the acknowledged-elision mode, per matrix).

## 12. Performance Requirements

- Budgets NFR-01–04 under L2 with an erasure and two exports concurrent; viewer indexes verified against the 100 M-entry synthetic corpus.

- Chain computation ≤ 0.1 ms/entry (canonicalization dominated); per-tenant lanes keep ordering without cross-tenant contention.

- Embedded timelines (FR-07) ≤ 150 ms p95 (object-index reads, first page).

- Hold-scope preview counts ≤ 2 s for tenant-wide scopes (approximate fast-count with exact-on-confirm).

- Sampled verification covers ≥ 5% of tenant-days nightly within NFR-03.

## 13. Accessibility Requirements

## 14. Localization Requirements

Action sentences via ICU-templated keys per action (en + am) with stable keys alongside in exports (the Doc 15 pattern); actor/object label snapshots render verbatim (operator content); timestamps per Doc 01 rules with UTC-exact on hover (audit is where seconds matter); the erasure verification report renders in the tenant default language with an English regulatory annex option; masking tooltips localized; the viewer’s relative times switch to absolute beyond 24 h (precision posture inverse to Doc 07’s casual surfaces).

## 15. Edge Cases

EC-01 Clock skew vs chain ordering → the chain orders by consumer-lane sequence, occurred_at is data not order (documented; the seal counts entries, not wall-time windows’ completeness). EC-02 A tenant-day with zero entries → sealed with count 0 (absence of activity is itself attestable). EC-03 Retention drop meets a hold created seconds before → hold check inside the drop transaction (Doc 04 EC-09 family); the race resolves to retention-skip. EC-04 Erasure of a customer merged into a survivor (Doc 08) → scope resolution walks tombstone pointers; the review shows the survivor-profile implication explicitly (erasing the merged tombstone’s data vs the survivor’s — a human-decided scope with both options rendered). EC-05 An erasure request for a customer with an active legal hold on their tickets → FR-16’s conflict surface; the recorded human decision references both instruments; neither silently wins. EC-06 Entry payload exceeding size sanity (a settings import diff of 5,000 keys) → payload stored as a summary + a pointer to the import’s per-row entries (FR §Doc 16 BR-07 already atomized it — the summary entry links the set via trace_id). EC-07 Canonicalization-version transition (T-04) → dual-hash period where both versions verify; seals record the version; the verify tool handles mixed ranges. EC-08 An audit.view holder losing the permission mid-investigation → next query 403s (Doc 03 propagation); saved investigations persist but render locked; no cached result access (the viewer never caches result payloads client-side beyond the open page). EC-09 A module emits a matrix key with missing required fields (reason absent on an escalation) → dev/CI throw (T-02); in production (defense-in-depth) the entry writes with a schema_violation flag + alert — an imperfect entry beats a missing one (BR-01’s spirit: the trail never has gaps, even ugly ones). EC-10 Subject export requested during that customer’s erasure execution → blocked with the state explanation (erasure supersedes; the verification report is the terminal artifact). EC-11 High-visibility fan-out (FR-05) with Doc 18’s feed down → entries write normally (the feed is a consumer, never a gate); the feed catches up from the stream (Doc 01 FS-02 family). EC-12 A verify mismatch caused by storage corruption vs tampering → the runbook’s first fork (compare against backups + anchor); the alert severity is identical until proven benign (assume the worst first).

## 16. Failure Scenarios

FS-01 Audit consumer down → business actions unaffected (FR-02); entries accumulate in the outbox; lag alert; on drain, chain order preserved by lane sequence; NFR-05’s reconciliation proves zero gaps. FS-02 Seal job failure → days stay pending (visible in the viewer); verification treats pending days as unverifiable-yet (never falsely ✓); alert at pending-age threshold. FS-03 Erasure stage failure (a purge hook errors) → checkpoint holds; the stage retries; sustained failure escalates with the partial-state report (checkpointed counts) — the workflow never claims completion it didn’t verify. FS-04 External anchor endpoint down → seals queue for anchoring (local seals remain valid); the anchor-lag is reported in verification reports during the window (honesty in the artifact). FS-05 Partition-management failure on the audit table → Doc 01 EC-10’s pre-created partitions + the monitor; the one table where a write failure would be an integrity event gets the widest pre-creation margin (6 months).

## 17. Success Scenarios

SS-01 A regulator audit: the officer receives a scoped export + verification report, independently re-verifies the day seals against the external anchor, and the meeting is about the operation, not the data’s trustworthiness. SS-02 US-02’s incident forensics: trace-id assembly reconstructs a cross-module causal chain (settings change → rule behavior → agent action) in minutes; the post-incident review cites entry ids. SS-03 A full erasure (US-04) executes with one legitimate conflict (a held dispute ticket) resolved by documented human decision; the customer receives the verification report; six months later, the backup-expiry date it promised has passed and a spot check confirms. SS-04 The FR-03 gate catches a real gap in development: a new bulk operation ships its matrix mapping and emission test because the build refused otherwise — SS-02’s future forensics quality was defended without anyone noticing.

## 20. Risks

R-01 Coverage rot as modules evolve (High likelihood) → the four-registries cross-check (NFR-06) + the runtime harness make rot unshippable; the matrix change-log is the human review surface. R-02 Audit volume cost (High/Medium) → changed-fields-only payloads (FR-04), partitioning, retention floors with tenant-raisable ceilings, and the EC-06 summarization pattern bound growth; volume metrics in Doc 15’s platform family. R-03 The erasure workflow becoming a rubber stamp (Medium/High) → mandatory four-eyes, the counts-and-justifications review screen, and verification reports create friction exactly where friction protects people; onboarding trains the *why*. R-04 Integrity theater (hash chains nobody checks) (Medium/Medium) → the *nightly sampled* verification + the visible seal-status column + SS-01’s external-anchor story keep the machinery exercised and legible. R-05 Privileged-reader misuse (Low/High) → high-risk permission, read-access summaries feeding anomaly rules (SEC-02), and the RG double-gate; the platform watches its watchers to the degree the trail’s own recursion allows.

## 21. Recommendations

- Build the coverage matrix + the runtime assertion harness in this module’s first sprint and backfill mappings for Docs 02–16’s already-specified events — the harness then becomes Doc 19’s shared oracle (US-07) and every module’s regression net.

- Ship hash-chaining and day seals from the first production write; integrity guarantees are only credible when they predate every entry they cover.

- Rehearse one full erasure and one regulator-style export on staging with the operator’s compliance contact before launch — the workflows’ review screens will improve more from one real walkthrough than from any amount of speculation.

- Configure external anchoring for every production tenant even where no regulator asks; SS-01’s “verify it yourself” posture is cheap insurance and a sales asset in a regulated vertical.

- Guard BR-04’s duality forever: the pressure to widen audit-read access (“managers should see everything”) is constant, and yielding converts an accountability system into a surveillance system — the platform’s answer is embedded timelines with provenance for all, and the full trail for the few with reason.
