# Document 19 — QA Strategy & Test Plans

**Product:** AI-First Support Platform for Betting Companies **Document series:** 19 of 19 · Standalone enterprise specification **Audience:** QA engineers, all developers, engineering leadership, product, the operator’s UAT participants **Depends on:** every prior document — their Acceptance Criteria are this document’s inventory, their golden fixtures its shared oracles, Doc 17’s coverage harness its audit oracle, Doc 18’s environments, gate inventory, load profiles, and drill calendar its execution substrate. Consumed by: the release process (Doc 18 FR-07/FR-08), engineering onboarding, the operator UAT. **Stack context:** Pest (unit/integration/property via pest-plugin), Playwright (browser incl. WebView lab), axe-core (a11y), the L1/L2/L3 generators (Doc 18 T-08), the coverage/assertion harnesses defined across the series

## 1. Executive Summary

This final document specifies how the platform is verified: the **test strategy** (a contract-first pyramid where the series’ Acceptance Criteria — some 190 AC items across Documents 01–18 — form the normative test inventory, each mapped to an owning automated suite in Doc 18’s gate registry), the **shared-oracle system** (the golden lifecycle fixtures Docs 06/12/15 co-own, the golden-conversation and injection corpora of Doc 09, the RG labeled corpus with its governance process, the hostile-theme/pseudo-locale sweep, the hostile-host widget page, the audit coverage harness as the universal side-effect oracle, and the synthetic 100 M-entry and 1 M-customer datasets), the **test-type catalog** with per-type standards (unit, property-based, contract, integration, browser/E2E, visual regression, accessibility, localization, security/red-team, performance against L1/L2/L3, chaos/resilience, and structured manual exploratory testing), the **per-module test-plan index** (every document’s ACs cross-referenced to suites, fixtures, environments, and cadence — CI-blocking, nightly, weekly, or drill), **quality gates and release criteria** (what green means for a routine release vs a migration-bearing one vs launch), **defect management** (severity taxonomy aligned to Doc 18’s incident severities, triage SLAs, the quarantine protocol for flaky tests), **UAT with the operator** (scripted journeys from the personas, staging with real Telegram/SMS, sign-off scope), and the **launch-readiness checklist** that assembles everything — gates, drills, fixtures, UAT, security floor, a11y/i18n sweeps — into the single go/no-go artifact. The strategy’s one-sentence version: **the specifications in this series are executable — QA’s job is to keep them running, and a claim without a running test is treated as untested.**

## 2. Purpose

- Convert the series’ ~190 Acceptance Criteria into one governed, cross-referenced test inventory with clear ownership, cadence, and environments — nothing verified twice by accident, nothing verified zero times by omission.

- Define the standards each test type must meet so suites stay trustworthy (deterministic, isolated, fast enough for their tier) as the codebase grows.

- Specify the human layers automation cannot replace: exploratory testing charters, UAT with the operator, and the fixture-governance rituals (especially the RG corpus).

## 3. Scope

**In scope:** strategy & pyramid; the AC inventory and traceability rules; shared oracles and fixture governance; test-type catalog with standards; the per-module plan index; test data management; environment usage (which tier runs where); quality gates & release criteria per release class; defect management & flake protocol; regression strategy; UAT design & sign-off; launch-readiness checklist; QA metrics (about the tests themselves); team practices (review rules, onboarding). **Out of scope:** the gate pipeline mechanics (Doc 18 FR-07/T-02 — this doc populates it); environment provisioning (Doc 18); the drill execution calendar (Doc 18 FR-23 — resilience *content* referenced here); production monitoring (Doc 18’s observability is production’s “test suite”; the boundary is deploy).

## 4. Functional Requirements

### 4.1 Strategy & traceability

FR-01 **Contract-first pyramid:** unit + property tests (fast, exhaustive on pure logic: SLA clocks, guard functions, routing determinism, chain hashing) → contract tests (the series’ interface freezes: adapter conformance, event schemas, handoff packet, metric formulas, API shapes) → integration (module pipelines on the ephemeral stack) → browser/E2E (the journeys) → the specialized sweeps (visual, a11y, i18n, security, performance) → chaos/drills (staging). Higher tiers verify wiring and experience, never re-verify logic the lower tiers own (the anti-duplication rule that keeps the 40-minute CI budget honest, Doc 18 NFR-02). FR-02 **Traceability:** every AC in Docs 01–18 maps to ≥ 1 automated test (or a justified manual/drill entry) in the **traceability matrix** — a code-registered index (the sixth registry, completing the constitution: permissions, settings, notifications, audit coverage, gates, tests) with {AC ref, suite path, type, tier, cadence, environment, owner}; CI fails on unmapped ACs when a document version bumps (specs and tests version together); the matrix renders as a living coverage report per document. FR-03 New-feature rule: code review requires the AC-or-new-AC question answered — behavior changes either trace to an existing AC’s updated test or add an AC to the owning document’s change log with its test in the same PR (the series stays executable as it evolves).

### 4.2 Shared oracles & fixture governance

FR-04 Oracle inventory (single-sourced, versioned in-repo, consumed by CI/staging/restore-verification per Doc 18 T-08): - **Golden lifecycle corpus** (Docs 06/12/15): scripted ticket lifecycles with exact expected timestamps, SLA states, and metric values — the three modules’ shared arithmetic truth. - **Golden conversations + injection red-team + transaction-fact traps** (Doc 09): dialog fixtures with expected action types at pinned configs; replay-mode in CI, live-provider nightly on staging. - **RG labeled corpus** (Doc 09 NFR-07): governed per FR-05. - **Routing determinism generator** (Doc 11 T-08): property-based org/traffic snapshots. - **Hostile-theme + pseudo-locale** (Doc 16 T-08) and **hostile-host page** (Doc 13): the two adversarial rendering environments. - **Audit coverage harness** (Doc 17 T-08): the universal side-effect oracle — module fixtures assert their exact audit entries, making “did the right thing happen” checkable everywhere. - **Synthetic scale datasets:** 1 M customers, 10 M messages, 100 M audit entries, 50 k KB chunks — generated deterministically (seeded) for the performance ACs. - **Encoding/segmentation corpus** (Doc 14), **Amharic search corpus** (Doc 08 AC-07), **DST/timezone date set** (Docs 06/12/15 fixtures). FR-05 **RG corpus governance** (the series’ most sensitive asset, Doc 09 Rec-3): labeled distress dialogs maintained under a documented process — additions/relabels require review by two people including the operator’s compliance contact; versioned with changelogs; access limited (repo-path permissions); precision/recall reports generated per version; threshold changes (Doc 09 T-06) always cite the corpus version they were evaluated against. The corpus is synthetic/anonymized by construction — no real player content enters it (FR-06’s rule applied at its strictest). FR-06 Test data rules: all fixtures synthetic; production data never becomes test data (Doc 18 FR-02/BR-06 — the sanitized-extract exception exists for *reproduction*, and reproduction artifacts are destroyed after the fix’s test lands as a synthetic fixture); personal-data-shaped fields in fixtures use obvious fabrications (the +251-90000xxxx range, @fixture usernames) so a leak is self-identifying.

### 4.3 Test-type catalog (standards per type)

FR-07 **Unit/property:** pure-logic isolation, no I/O; property tests mandatory for the series’ named pure libraries (SLA clock, guard function, chain canonicalization, routing determinism, interval math); mutation-testing sampled quarterly on these libraries (the tests’ tests). FR-08 **Contract:** interface fixtures pinned as data (recorded payloads, schema versions); both sides of every internal contract run against the same fixture files (producer and consumer cannot drift apart unnoticed — the Doc 01 R-02 containment generalized). FR-09 **Integration:** ephemeral full stack (Doc 18 FR-01 CI environment) with real Postgres/Redis and the mock providers; each module’s pipeline ACs; the isolation/RLS suite runs here per deploy (Doc 01 AC-01’s placement). FR-10 **Browser/E2E:** Playwright on the support matrix + the WebView lab (Doc 13 NFR-05); journeys own *experience* assertions (states, focus, announcements) while API-level integration owns data assertions — one behavior, two lenses, no duplication (FR-01’s rule); the complete-shortcut sweep (Doc 07 AC-08) and the widget flow states (Doc 13 AC-05) live here. FR-11 **Visual regression:** the §8-state screenshot suites every document specified, executed across light/dark × en/am/pseudo-locale × the density modes where relevant; diffs reviewed with a strict update protocol (a visual change requires the owning doc’s §8/§9 review, not a snapshot rubber-stamp). FR-12 **Accessibility:** axe-core automated floor on every browser suite + the manual screen-reader passes (NVDA + VoiceOver per Doc 13 §13) on the four highest-traffic surfaces (login, inbox, widget, Backoffice settings) per release; keyboard-only journey runs for the core loops; the contrast validator’s own correctness (Doc 16 AC-03) tested against a known-ratio palette set. FR-13 **Localization:** the pseudo-locale sweep (truncation/overflow/RTL), completeness-gate fixtures (every module’s gate), ICU message-format validation (grammar-slot tests for the sentence-templated surfaces: routing records, audit sentences, SLA examples), and the Amharic content passes (search, encoding, SR pronunciation spot-checks in the manual layer). FR-14 **Security:** the continuous internal floor — enumeration/timing (Doc 02 AC-01), scope matrices (Doc 03 AC-03 fixtures reused platform-wide), the injection red-team (Doc 09 AC-07), scrubber seeds (Docs 02/18), SSRF/egress (Doc 18 AC-06), immutability physics (Doc 17 AC-02), the widget origin defense-in-depth (Doc 13 AC-03) — plus the annual external pen test (Doc 18 SEC-06) whose findings convert into permanent fixtures here. FR-15 **Performance:** L1 micro-benchmarks pinning the named p99/p95 budgets (every NFR with a number has a benchmark with an alert threshold at 80% of budget — regressions surface before they breach); L2 full-envelope on staging per release window (Doc 18’s soak) asserting all budgets *simultaneously* (Doc 18 AC-07’s integration proof); L3 semi-annual burst drill asserting the degradation contracts (honest states, zero silent failures). FR-16 **Chaos/resilience:** the drill calendar’s scenarios (Doc 18 FR-23) with their pass criteria drawn from the FS-sections’ specified behaviors — QA owns the assertion scripts, Doc 18 owns the calendar; the standing in-pipeline chaos: consumer-kill reconciliation (Docs 01/17), deploy-during-soak (Doc 18 EC-01), socket-kill fallback (Doc 13 AC-08). FR-17 **Manual exploratory:** chartered sessions (time-boxed, persona-framed: “Sara’s worst shift”, “Hanna reorganizes everything”, “a hostile visitor”, “the anxious player at 2 AM”), logged with findings-to-fixture conversion targets (an exploratory find that ships a fix must ship its regression test); cadence: per release window on staging, focused by the release’s change surface.

### 4.4 Per-module plan index

FR-18 The index (the traceability matrix rendered by document): for each of Docs 01–18 — its AC list, the owning suites per AC, tier/cadence/environment, the fixtures consumed, and the manual/drill entries where automation is justified-partial (e.g., Doc 05 AC-03’s real-device Business-connection walk: automated against staging Telegram nightly, *and* the quarterly physical-device drill; Doc 17 AC-05’s erasure: automated per class in CI, *and* the pre-launch staged walkthrough with the compliance contact). The index is generated from the matrix registry — it cannot drift from reality because it *is* the registry rendered.

### 4.5 Gates, releases, defects

FR-19 Release classes & criteria: **routine** — full CI gate inventory green (Doc 18 FR-07), no open Sev-1/2 defects in the change surface, visual diffs reviewed; **migration-bearing** — routine + the shadow-run lock report reviewed + two-person approval (Doc 18); **launch/major** — the launch-readiness checklist (FR-22). The error-budget freeze (Doc 18 BR-05) overlays all classes. FR-20 Defect taxonomy aligned to Doc 18 severities: Sev-1 (data integrity, cross-tenant, security, money-path correctness — e.g., a wrong SLA breach, a leaked note) — fix-forward immediately, incident process; Sev-2 (a module’s contract broken, a channel degraded, an AC regression) — blocks the next release of that surface, fix ≤ 3 days; Sev-3 (cosmetic, minor UX) — scheduled. Every Sev-1/2 fix ships with its regression test (the FR-17 rule universalized); defect metrics (found-by-tier, escape rate to staging/production) reviewed monthly — a production escape means a tier failed and the retro asks which. FR-21 Flake protocol (Doc 18 EC-06 owned jointly): quarantine lane, 2-week SLA, owner assigned, gates never weakened; quarantine-lane size is a tracked health metric with a hard cap (> 10 items pauses feature merges to that surface — flake debt is debt).

### 4.6 UAT & launch readiness

FR-22 **UAT:** conducted on staging with the real integrations (the staging bot, the gateway sandbox, real AI on staging keys) by the operator’s people in their personas — scripted journeys derived from the series’ user stories (Abel’s deposit journey end-to-end incl. the SMS; Sara’s full shift on the keyboard map; Dawit’s match-night with pull-ins; Hanna’s zero-code workflow build [Doc 12 SS-01’s hour]; the erasure walkthrough with the compliance contact; the rebrand-and-rollback) + free exploration windows; findings triaged per FR-20; sign-off scope = the journeys pass + no open Sev-1/2 from UAT; UAT is also the operator-training dry run (the sessions double as onboarding material capture). FR-23 **Launch-readiness checklist** (the go/no-go artifact, each line owner-signed): all gates green on the release candidate; the traceability matrix 100% mapped for Docs 01–18 at their launch versions; L2 validated on production sizing (Doc 18 AC-07); the first full drill cycle completed with actions closed (Doc 18 AC-10); restore drill inside RTO with decryption (Doc 18 AC-05); security floor green + external pen-test findings closed or accepted-with-sign-off; a11y manual passes on the four surfaces; en+am sweeps green incl. the SMS encoding corpus; the RG corpus at its reviewed version with precision ≥ target (Doc 09 NFR-07); seeded content in place (KB starters + the operator’s top-20 [Doc 10 Rec-2], seeded forms/rules, config bundle); UAT signed; the incident page functional (Doc 16 AC-10); comms templates incl. Amharic staged (Doc 18 §14); the vendor register current; the per-market checklist for Ethiopia complete (Doc 18 FR-30). No line, no launch.

## 5. Non-functional Requirements

NFR-01 CI tiers within Doc 18 NFR-02’s budgets (full inventory ≤ 40 min; unit+contract ≤ 8 min for the inner loop); nightly class ≤ 4 h. NFR-02 Determinism: zero tolerance for time/order/randomness flakes by construction — frozen clocks, seeded generators, explicit waits-on-signal (never sleeps) as suite standards; the flake protocol handles the residual. NFR-03 Test-code quality: suites are production code (reviewed, refactored, owned); coverage is tracked per module but **AC-mapping is the governing metric** (line coverage informs, traceability governs — a stated stance against coverage theater). NFR-04 The traceability matrix’s own freshness: document-version bumps without matrix updates fail CI (FR-02); the rendered index regenerates per merge. NFR-05 Oracle stability: golden fixtures change only via the owning documents’ change control; a fixture change PR must reference the spec change that motivates it (fixtures are law, amended formally). NFR-06 The full launch checklist (FR-23) is executable in ≤ 2 weeks of calendar time from a green candidate — readiness verification must not itself become the schedule risk (parallelization documented per line).

## 6. User Stories

US-01 As a developer, my inner loop (unit+contract, 8 min) tells me I broke a spec before I context-switch; the pipeline’s failure message cites the document and AC (Doc 18 §8’s teaching pipeline realized). US-02 As a QA engineer, I don’t invent what to test — I keep 190 executable claims true and hunt for the claims the documents missed (exploratory charters), converting finds into new claims. US-03 As engineering leadership, the coverage report per document tells me exactly which promises are verified at what cadence — and the escape-rate review tells me which tier to strengthen. US-04 As the operator’s compliance contact, I have personally walked the erasure flow and reviewed the RG corpus my chatbot’s conscience runs on, before a single real player touched the system. US-05 As the platform owner, go/no-go is a checklist of signed facts, not a meeting of feelings. US-06 As a future team member, the traceability matrix + the plan index are my map of the entire system — the tests are the onboarding docs that can’t be stale.

## 7. Business Rules

BR-01 **A claim without a running test is untested** — the series’ ACs are promises, and this document’s matrix is the only place “verified” gets to mean anything; marketing, sales, and operator conversations may cite only matrix-green claims. BR-02 Tests trace to specs, specs govern tests (FR-02/03/NFR-05): the documents and the suites version together — divergence in either direction fails the build, so the series stays the truth. BR-03 No tier re-tests another’s job (FR-01): duplication is a review-rejectable defect — it bloats budgets and, worse, creates two answers to one question. BR-04 Real player data never enters testing (FR-06) — no exception has ever improved a test suite enough to justify the breach it normalizes. BR-05 Flakes are debt with a cap (FR-21); a gate is never weakened to accommodate one (Doc 18 BR-01’s QA half). BR-06 The human layers are mandatory, not fallback: exploratory charters, screen-reader passes, the UAT journeys, and the physical-device drills verify what automation structurally cannot; skipping them is a launch-checklist failure, not an efficiency. BR-07 Escapes teach (FR-20): every production escape gets a tier-attribution retro; the fix without the “which net had the hole” answer is half a fix.

## 8. UX Requirements

(This module’s users are the team; its surfaces are reports and tools.) - **Coverage report** (per document): AC list with status chips (green/red/quarantined/manual-drill), suite links, last-run, cadence — the FR-18 index rendered; a document-level roll-up header (“Doc 06: 9/9 AC verified, 2 nightly, 1 drill”). - **CI failure messages:** the Doc 18 §8 contract (AC reference + fix-locality hint) is a QA-owned standard — failure copy is reviewed like UI copy. - **Flake quarantine board:** items with age, owner, SLA countdown; the cap’s proximity visible. - **Exploratory session log:** charter, notes, findings with their fixture-conversion status. - **UAT runner:** the scripted journeys as checklists with per-step pass/fail/notes, findings feeding triage directly. - **The launch checklist:** the FR-23 lines with owner-signature states — deliberately boring, deliberately unskippable.

## 15. Edge Cases

EC-01 An AC that is genuinely untestable as written (discovered during mapping) → the finding goes back to the owning document as a spec defect (the AC is rewritten testably or split); “untestable” is never a matrix status. EC-02 Two documents’ ACs overlap (the shared-fixture seams: Doc 06/15 timestamps) → one suite owns execution, both ACs reference it (the matrix supports many-to-one; duplication per BR-03 is the error, shared ownership is the design). EC-03 A golden fixture fails after a *correct* behavior change → the NFR-05 protocol: the spec change lands first (document change log), the fixture change references it, both in one reviewed PR — the order is the point. EC-04 Live-provider nightly goldens fail on provider-side drift (Doc 09 EC-11’s model behavior shift) → triaged as vendor drift, not regression: the replay-mode goldens localize whether *we* changed; the vendor register review (Doc 18 FR-29) receives the finding; thresholds/prompts adjust via Doc 09’s simulation discipline. EC-05 The WebView lab device fleet ages out of the support matrix → matrix updates follow Doc 13 NFR-05’s pinning process; retired entries’ last-green results archived. EC-06 A drill “fails” (restore exceeds RTO) → that is the drill *working*: a Doc 18-tracked deviation with actions, and the launch checklist blocks on closure if pre-launch — drills are tests whose failures are findings, never embarrassments (the blameless posture extended to rehearsals). EC-07 An exploratory finding contradicts a green AC → both can be true (the AC verified too narrowly); the finding tightens the AC’s test *and* files the experience defect — the matrix’s green was honest for what it claimed, and now it claims more. EC-08 UAT participants go off-script and find gold → encouraged by design (the free-exploration windows); off-script findings enter the same triage; the script absorbs the best detours next cycle. EC-09 A quarantined flake turns out to mask a real race → the quarantine protocol requires root-cause, not suppression (the 2-week SLA is for *diagnosis*); races found this way are Sev-2 minimum with the reconciliation harnesses (Docs 01/17) as the verification pattern. EC-10 The matrix registry itself breaks (rendering bug) → CI treats matrix-generation failure as a red gate (the constitution’s registries are load-bearing; their tooling is tested too — registry unit tests exist, turtles bounded at this level).

## 16. Failure Scenarios

FS-01 CI fleet degradation slowing tiers past budgets → the Doc 18 FS-04 posture (no gate, no ship) with the emergency path; QA’s contribution is tier-priority guidance (which suites are the minimum floor for the hotfix path’s retroactive run). FS-02 A shared oracle corrupted (bad merge to fixtures) → NFR-05’s change control makes it reviewable history; revert + the fixture-integrity check (checksums in the oracle packages) catches silent corruption at load. FS-03 Staging’s real integrations down during a release window (Telegram staging bot, gateway sandbox) → the affected nightly/UAT items mark blocked-external with the mock-tier results standing as the floor; launch-class releases wait (the checklist’s lines don’t accept substitutes); routine releases proceed on the CI inventory (which never depended on external services by design). FS-04 Defect-tracker/matrix drift (fixed defects without regression tests slipping through) → the FR-20 ship-with-test rule is a PR-template check + a monthly audit query (closed Sev-1/2 without linked tests = process defects, reviewed). FS-05 Team attrition hitting suite ownership → the matrix’s owner field + the per-document namespacing make orphaned suites visible; ownerless entries are a tracked health metric (the human single-points surfaced like the technical ones).

## 17. Success Scenarios

SS-01 Launch go/no-go takes forty minutes: every checklist line pre-signed, the two open questions answered from the coverage report and drill logs — US-05’s meeting of facts. SS-02 Six months post-launch: escape rate trending down, the tier-attribution retros have strengthened the integration net twice, the quarantine board sits at 3 items, and the matrix shows 214 ACs (the spec grew 24 claims from findings — the FR-03/EC-07 loop visibly working). SS-03 A Doc 09 provider swap (EC-04 → vendor exit) executes with the golden suite as the acceptance harness for the replacement — the corpus that guarded quality now *measures the migration*, and the operator never notices. SS-04 A new senior engineer onboards by reading three documents and running their suites (US-06); their first PR adds an AC with its test, correctly, because the machinery made the right way the obvious way.

## 20. Risks

R-01 The matrix becoming ceremony (High likelihood over years) → the governing-metric stance (NFR-03), the escape retros (BR-07), and SS-02’s growth loop keep it a living instrument; a matrix nobody argues with is the warning sign, reviewed annually. R-05 The RG corpus’s dual sensitivity (quality-critical and content-sensitive) (Low/High) → FR-05’s governance + SEC-03’s handling; the corpus review ritual with the operator’s compliance contact is the standing safeguard — and the relationship it builds is itself risk mitigation.

## 21. Recommendations

- Stand up the traceability matrix and map Docs 01–03’s ACs in the project’s first two weeks — the habit of executable specs is set by the first modules or never; retrofitting traceability onto a mature codebase is the expensive order everywhere in this series, and here most of all.

- Hire or designate QA ownership that reviews *specs*, not just code — this strategy’s QA engineer is a co-author of the documents’ change logs, and the role’s seniority should match.

- Run the full launch checklist once as a rehearsal a month before the real candidate (NFR-06’s parallelization discovered by doing) — the go/no-go meeting’s calm (SS-01) is manufactured in that rehearsal.

- Protect the inner loop’s 8 minutes as a hard product of this strategy — developer trust in the pipeline is the multiplier on everything else here, and it is lost at minute twelve.

- When the series and the system diverge — and they will — fix whichever is wrong *through the change machinery both share*; the entire architecture of these nineteen documents rests on that one discipline, and this document exists to make it enforceable.
