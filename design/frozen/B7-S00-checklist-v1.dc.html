The four absences, and where each one is visible

Both documents define this product partly by what it refuses to do. A refusal that is merely absent from a design reads as an oversight, so each is stated on the surface where a person would go looking for the missing thing:

  • No impersonation, anywhere. Doc 02 SEC-07 makes it a published security stance, not an unbuilt feature. Not in the admin actions, not in the devices table, not in the branding preview. Stated once, plainly — row H06.
  • No contrast override. Doc 16 BR-02: the one validator with no escape hatch. The publish dialog has no “publish anyway” — it has failing pairs and nearest-passing suggestions. Rows L05, S06.
  • No admin-set passwords, no visible secrets. Doc 02 BR-02: admins trigger resets, never choose. The admin surface offers a reset, an unlock and a 2FA clear — and says why there is nothing else. Rows D06, E09, H02.
  • No account-existence disclosure. Doc 02 FR-02 / SEC-01 / AC-01: one generic message on login, one uniform response on reset, byte-identical either way. There is no “user not found” variant to design, and the copy has to not read as evasive. Rows A08, E01, E02.

Four questions before I design anything — asked one at a time

Each is a place where a document is silent, or where your Step 2 rule and a document say different things. None is a preference; each changes what is in the contract. I am asking Q1 in chat now and holding the rest until it is answered.

Q1 — asked now · does Section H get a host screen, or only its actions?

Doc 02 names five administrator actions on someone else's account — unlock (FR-03), trigger a reset (FR-16), clear 2FA with a typed-name confirmation (FR-08), invite and resend (FR-17), disable, which revokes sessions and tokens atomically (BR-04, FR-05). It never names the screen they live on: there is no user list, no user record page, no roster anywhere in Doc 02. Batch 6 closed its Silence 1 by ruling that user administration is Batch 7 and pointed at exactly these clauses (B6-S00-checklist-v2). So the actions are certainly mine; the container may not be. Either answer is a clean contract — H01–H06 as actions hosted on a user's existing profile, or H01–H06 plus a user list and record page as new screens. I will not guess, because inventing a roster the documents never describe is the failure this program forbids.

Q2 — held · the branding editor at 375

Doc 16 §9: “branding editor desktop (previews need room; fat-finger policy family)”. Your Step 2: both viewports together, a weak mobile version is a rejection. In Batch 6 you ruled that the documents hold for the five editing surfaces, and they shipped 375 read-only behind Doc 03 §9's explicit “editing requires a larger screen” notice. That ruling was scoped to Batch 6, so I am asking whether it carries to Sections J–U rather than assuming it. The auth screens are unaffected either way — Doc 02 NFR-05 requires every auth screen fully functional in a mobile browser, and they will be.

Q3 — held · are the three auth emails designed, or previewed only?

Doc 02 §14 names three: invite, reset, new-device — per language, tenant-branded. Doc 16 FR-01 owns their header, footer, address block and legal line, and §8 previews them. Neither document owns their body copy explicitly. Section I designs all three as full templates in both languages; the alternative is designing only the branded chrome and showing the bodies as slots. Section I is written the first way and is one deletion away from the second.

Q4 — held · API tokens are in, unless you read the scope line more narrowly

Your scope line says “login, two-factor, recovery, reset, device/session management — whatever the document names”. Doc 02 §4.5 also names personal and machine tokens, with visible obligations: plaintext shown once, last-used displayed, individually revocable, a rotation flow with an overlap window. They sit on the same profile → Security page as the devices table, so I have contracted them as Section G. On the narrower reading, G01–G11 come out and the section disappears.

What I have deliberately left out

  • Auth machinery with no human surface. Widget visitor tokens (Doc 02 §4.6), inbound webhook authentication (§4.7) and the auth event bus (§4.8) are backend contracts. The one place webhook auth becomes visible — the per-bot secret at registration — shipped in Batch 6's add-bot wizard and is not rebuilt.
  • The rest of Doc 16. Settings, notification preferences, feature flags, the translation manager, config export/import and the incident page are Batch 6 and are frozen. This batch touches Doc 16 only where the branding editor and its validators live. The auth.* keys render in Batch 6's Security group; Sections A–I show the consequences of those keys, never a second copy of the settings rows.
  • Surfaces the branding inventory only references. Widget appearance is Doc 13 FR-19, AI persona content is Doc 09 FR-18, SMS sender IDs are Doc 14, exports, watermarks and PDF transcripts are Docs 04 and 15. FR-02 requires each to appear in the inventory as a live thumbnail with a link out — a reference, not a rebuild. Cross-walk 3b, carried over from B6-X01-crosswalks-v2, holds each to exactly one owner.
  • Build obligations. Guards and middleware order, argon2id tuning, session and token budgets, CSP and HSTS, the k-anonymity breach check, GeoIP plumbing, the CI string-lint and the hostile-theme sweep are engineering contracts, not screens — except where a document turns one into something a person sees, like “location unavailable” when GeoIP is down (F09) or the ten-second scope-propagation bound (G08), which are rows.
  • The audit trail itself. Doc 02 §4.8 and Doc 16 SEC-01 feed a dedicated audit view; that view is Doc 17 and is not in the seven-batch program. This batch states on the surface that a change is recorded, and by whom.
  • Both §19 future lists. SSO and SAML, WebAuthn and passkeys, step-up auth, adaptive auth; custom font uploads, per-department sub-branding, a theme marketplace, scheduled publishes, translation memory, per-tenant custom domains. Out of v1 and absent — except where a document requires the absence to be visible, as with the curated-fonts-only note at L02.
  • Impersonation. Not an omission, a stance — Doc 02 SEC-07. It is a row precisely so the closing audit records that it was deliberately not built.
