Branding — degraded states

What the operator sees when the theme layer itself is having a bad day, and the proof that no combination of their choices can break a screen. Four rows, and the through-line is that branded-but-generic is a designed state, not a failure — a platform that renders unbranded is working; a platform that renders half-branded is not.

The hostile-theme row is the interesting one. Doc 16 FR-05 and T-08 ask the build to survive a garish palette, a very long legal name and long Amharic — usually verified in CI against a snapshot. Verified there it stays invisible, so it is drawn here: the ugliest publishable theme in the product, rendering correctly.

Built on B1-DS v4, under the Section S standing rule: status hues stay with their semantic components. Parity checked claim by claim against the file.

U03 · nothing hardcoded — how it was actually checked
Not a claim, a sweep. Every colour literal in this batch's twenty-one files was matched against the B1-DS token table; the eight files where a literal appeared outside a token were corrected and disclosed in their own notes. What remains are the deliberately fixed tokens — the eight status families, priority dots, SLA and reply-window chips, connection state, channel health, internal note, and the violet AI accent — and Section L names each one on the surface where an operator would try to re-skin it.
The rule that makes this testable: a theme changes values, never layout. No token in Doc 16's set can move an element, change a size or hide a control — which is why the hostile frame above needed no special-case CSS to survive.

Delivery note

Delivered: all four rows, both themes. U01 in §A at 1440 light; U02 and U03 in §B at 1440 dark in Amharic — the hostile theme with a 59-character name and long Amharic on every surface; U03 and U04 in §C.

Two corrections after review, and one open question for you. The hostile magenta shipped as #E040A0 under a claim of 5.2:1; computed, it is 3.88:1 — the exact pair Section L refuses and Section S blocks, which made the frame unpublishable and the row pointless. It is now #C4007A at a computed 5.79:1, still garish, genuinely publishable. Separately, the dark frame’s fixed tokens had been mixed by eye into dark variants (#17301F, #241C3D and others) that exist in no B1-DS version — asserting token fidelity with invented hexes, on the one row whose subject is token fidelity. They now carry the B1-DS values verbatim.

A third correction: the hostile length was asserted, not built. The frame claimed a 74-character name that truncated behind a tooltip; measured, the name was 25 characters, nothing overflowed, no ellipsis rendered and no tooltip existed — so the row’s central condition was never exercised while its judgement paragraph reasoned about it. The name is now 59 characters and genuinely overflows the 210 px top bar, the full string is on the element as title and aria-label with tabindex="0" so a keyboard can reach it, and the footer carries it in full. The footer links now carry both languages, as the caption said they did.

v2 — the dark tokens were in B1-DS all along, and I twice failed to look. This section first invented dark variants by eye, then “corrected” them to the light values while raising a question about whether dark variants should exist. B1-DS v2 §2 carries a complete dark column — every status pill, priority dot, SLA and reply-window chip, connection state, channel health rollup, note token and the AI accent, each with its own dark value. The frame now uses them verbatim. The open question I raised at Section U is withdrawn: there was nothing to specify, only something to read. That is the second time in this batch a token was mixed by eye when the answer was in the file, and it is the failure the program’s own first rule exists to prevent.

One deviation, flagged: no 375 frame in this section. Each row is a state of a screen delivered elsewhere — the inbox, the inventory — and both already ship at 375 in their own sections; drawing the phone again would restate them rather than prove anything about degradation. Say the word and it ships.

One judgement. The long company name does truncate — in the top bar, at 210 px, with the full string in a tooltip and in the footer. FR-05 requires that nothing break, not that everything render in full; a 59-character name shown complete in a 52 px top bar would push the search field off the screen. The distinction worth auditing: truncation with the full value reachable is a layout decision, silent loss is a defect.

Parity, claim by claim. Three claims. Branded-but-generic is a designed state — English in §A's banner, Amharic not applicable: the banner is admin-facing and this tenant's admins read English, so U01 ships English-only and I am stating it rather than implying coverage. Every meaning token survives a re-skin — English in §B's caption and §C's panel, Amharic in the hostile frame itself, where all four tokens render in Amharic. A failed preview says so in place — English in §C; no Amharic surface, same reason as U01.
