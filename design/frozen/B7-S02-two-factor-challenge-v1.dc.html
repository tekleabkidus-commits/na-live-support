The two-factor challenge

Six digits, typed with one thumb while holding a phone in the other hand, at 07:03, by someone who is already late. That is the whole design brief. The card is Section A's card in its second step — same width, same chrome, same footer — because a challenge that looks like a different screen makes people think something went wrong.

Two things drive every decision here. The input is six boxes to look at and one field to operate — paste works, arrow keys work, and a screen reader meets a single labelled input rather than six unlabelled ones. And the failure path never becomes a countdown to disaster: attempts remaining are stated plainly, the recovery code is offered before it is needed, and the fifth failure explains itself instead of dumping someone back at the start.

Amharic is real text and is flagged for native review. Components are B1-DS verbatim plus the four additions proposed in Section A §F; the segmented input is proposed here as a fifth.

§A

Waiting for the code — 1440, both themes

B01 · B02 · B06 · B10 · Doc 02 FR-07, §8, §9, §13

Focus lands in the first box on arrival, so a typed code needs no click. Paste fills all six from anywhere in the field. The sixth digit submits — there is no button to reach for, but the escape routes stay visible the whole time: back to the password step, the recovery-code path, and the one line of help that names clock drift, the actual cause when a correct-looking code keeps failing.

§B

Verifying, success, and the four wrong codes before the fifth

B03 · B04 · B05 · Doc 02 FR-07, AC-03, §9

Attempts remaining are stated from the first failure, because the alternative is someone discovering the limit by hitting it. The count is text, not a shrinking bar — and it never appears on the login card, where it would tell an attacker how close they are. Success is a 400 ms check in place of the boxes; under reduced motion it simply is a check, with no transition.

Why this message is longer than the others

Three facts have to land at once: the attempt is over, the person is not locked out yet, and there is a way through that does not need the authenticator. Splitting that across two screens is how people end up locked out while holding a working recovery card in their wallet. It is the one place in this section where I chose length over brevity, and I would rather you reject it than have me trim it silently.

Note what it does not say: nothing about how many lock-out attempts remain. That number is the attacker's information, and Doc 02 FR-03 keeps it off the card.

§C

The recovery path — for the phone that is gone

B07 · B08 · B09 · Doc 02 FR-07, US-02, AC-03

A recovery code is read off paper, usually under pressure, usually one-handed. So the field is monospace, spaced in two groups of four, and case-insensitive — and the screen says out loud that each code works once, before it is used rather than after. The remaining count is the honest part: eight becomes seven becomes six, and at two the platform starts asking for new ones instead of waiting for the person to run out.

Where this banner lives

Doc 02 FR-07 says a banner prompts regeneration at two codes remaining, and does not say where. It appears on the first screen after signing in and on the profile security page — not on the challenge itself, where someone is mid-task and cannot act on it, and never on the login card, where it would announce to anyone typing an email that this account is two codes from being stuck.

That placement is my reading of a silence, not something the document states. If you want it somewhere else, this is the row to say so on.

§D

375 and 320 — six segments hold at both

B01 · B02 · B10 · Doc 02 §9, NFR-05

Doc 02 §9 sets a hard floor most designs quietly break: the code input stays six segments at 320 px. At that width the card's inner measure is 260 px once both borders are counted, so each segment lands at 38.3 px wide and 46 px tall — narrower than comfortable, still six, still tappable, and never wrapped to two rows or collapsed into one box. The 320 frame is included because it is the width where the rule either holds or does not.

§E

The segmented input — proposed as B1-DS addition 05

Doc 02 §9, §13
05 · Six-segment code input
Six boxes, gap 7 (6 at ≤ 320), each radius 6 on #CFCBC1, height 46 desktop / 52 mobile / 46 at 320. Filled digit 17/600. Active box takes the #22211D border — the same focus ink as the Section A field. Error: every box takes #C93B3B and the message goes in the B1-DS error banner above. Dark: #232320 on #45443E, active #ECEAE4, error #E06B6B.
B02 · one field, six boxes
The boxes are presentation. Underneath sits a single visually-hidden input with aria-label="Authentication code, 6 digits", inputmode="numeric" and autocomplete="one-time-code", so a screen reader announces one field, a password manager fills it, and iOS offers the SMS-style autofill chip. Six separate inputs would break all three.

Delivery note

Delivered: all ten rows. B01, B02, B06 and B10 in §A at 1440 in both themes and both languages; B03, B04 and B05 in §B; B07, B08 and B09 in §C; the mobile and 320 proofs in §D. Every message is announced, every count is text, and no state anywhere reveals lock-out distance.

Deviations, flagged: two, both upward. The recovery-code field is 44 px on desktop as well as mobile — it is transcribed from paper and the extra height is worth more than consistency with a 38 px form field. Mobile segments are 52 px rather than 46. Both exceed the floor rather than breaching it; neither changes a colour or a shape.

One silence I have read, and want confirmed: Doc 02 FR-07 requires the two-codes-left banner but never says where it appears. I have put it on the first screen after signing in and on the profile security page, and kept it off both the challenge and the login card, for the reasons in §C. Tell me if you read that differently.
