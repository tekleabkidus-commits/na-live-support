The login card

One card, eighteen rows, and the most-seen screen in the product — five hundred agents open it inside ten minutes at shift start, most of them on a phone. Everything here is B1-DS Direction C verbatim: the button, the banner, the skeleton, the pill, the type scale, the 4pt spacing. Four things had no home in the system yet — three form fields and a link colour for dark surfaces — and are proposed as additions at the foot of this file rather than quietly invented.

The tenant is Selam Bet, an Ethiopian sports-betting operator, and everything branded on this card — the logo slot, the welcome line, the footer links, the copyright — is read from its published theme, never written into this screen. The card itself is neutral: it has to sit under any brand without looking designed for one.

Amharic is real text and is flagged for native review. On your approval these frames export as the Doc 02 AC-09 baselines — en + am × light + dark.

A01–A06 · Doc 02 §8, §9 · Doc 16 FR-01

§C

The four refusals — both themes, both languages

A08–A12 · Doc 02 FR-02, FR-03, FR-05, SEC-01, SEC-05

Shown as the card's message region — everything above and below it is unchanged from §A. Light cells are English, dark cells are Amharic, so each state is proved in both themes and both languages at once. Every message is announced, carries a glyph as well as its tint, and none of them says whether the account exists. The hardest part of this section was copywriting: a generic message can easily read as evasive, so each one names what the person can do instead of what the platform knows.

A12 · blocked by an IP allowlist — deliberately indistinguishable from A08

Doc 02 SEC-05

There is no A12 frame, and that is the design. Doc 02 SEC-05 requires an IP-blocked attempt to return the generic error — byte-identical to A08 — because a distinct message would tell an attacker that an allowlist exists and that they are outside it. The event is audited as auth.ip.blocked where an administrator can see it; the person at the card sees exactly the A08 card above. Drawing a separate screen here would have been the failure, so the row is delivered as a stated absence rather than a picture.

§F

Three components the system did not have yet

proposed as B1-DS additions · not restyles

B1-DS v2 and both addenda have buttons, banners, toasts, skeletons, pills, tables and the search field — but no labelled form field, because until now nothing in the product asked someone to type their own credentials. Nor does it define a link colour for dark surfaces. Rather than matching by eye off a Batch 6 screen, which is the exact drift B12-R01 corrected, these four are built from existing metrics and proposed here for promotion. Every value below is taken from something already approved.

01 · Labelled text field
Label 11.5/600 #4A4842, 5 px above the control. Field: #FFFFFF on #CFCBC1, radius 6, padding 9 × 11, 13 px text, min-height 38 desktop / 44 mobile. Error: border #C93B3B, message in the B1-DS error banner, role="alert", never tint alone. Dark: #232320 on #45443E, error #E06B6B.
Derived from the B1-DS search field (radius, padding, type) and the error banner (hues). Nothing new was invented but the label pairing.
02 · Password field with visibility toggle
The 01 field with 40 px of right padding and a 32 × 30 ghost button inside it (44 × 44 on mobile, per the program floor). The toggle is a real button with an aria-label that changes with state, not an icon-only affordance.
Ghost-button colours are B1-DS ghost verbatim: #6B675D light, #A6A296 dark.
03 · Checkbox with consequence line
16 px box (20 px mobile), radius 4, border #CFCBC1; label 12.5/500 with an 11.5 px consequence line beneath it. The whole block is the touch target and clears 44 px on mobile.
The consequence line is the same pattern Batch 6 used under settings keys — one visual language for “here is what this does”.
04 · Link colour on dark surfaces
B1-DS sets a to #2F5AC8 / hover #1E3E92 and stops there — that blue fails on #1C1C19. Dark surfaces use #A9C0F5, the value already in B7-S00-checklist-v2, so this batch carries one dark-link value rather than two. Light is unchanged.
Caught in review: an earlier draft of this file used a second, undeclared blue. Declaring it is the point of this section.
A03 — delivered in part, and I am not marking it ✅
The row pairs the visibility toggle with the localized strength meter. The toggle is here, on the card. The meter is not — nobody chooses a password while signing in, so putting one on this card would be an invention. It has a truthful home on the set-password screen and ships there with Section E. The row stays open until it does.

Deviations, flagged: one. Mobile raises the B1-DS 36 px button and 38 px field to 44 px, per the standing program floor; desktop keeps the approved metrics exactly. Nothing else departs from B1-DS, and no approved element was restyled.

Two things I want your eye on. First, the logo slot is a dashed placeholder, deliberately: the mark comes from the tenant's published theme and drawing one here would invent brand personality this card must not have. Second, the generic error copy — “We couldn't sign you in with those details” — is the single sentence an agent will read more than any other in this product. It is honest, it names the next action, and it discloses nothing. If it reads wrong to an Amharic speaker, that is the one string I would most like changed before it becomes an AC-09 baseline.
