§C

The error rate, stated

14 corrections after a note had passed

Every one of these was a delivery note claiming something the file did not do, caught by measurement afterwards. Grouped by kind, because the pattern is more useful than the list:

  • Fixed tokens mixed by eye — 4. Three status-hue leaks onto generic glyphs (L, R, S), and S21's dark tokens invented, then "corrected" to light values, when B1-DS §2 had a complete dark column all along. The worst class, because it is the one thing the program's first rule forbids.
  • Counts written from expectation — 5. A 5.2:1 ratio that was 3.88:1; a 74-character name that was 25; 61 characters that were 59; two frame sums (40/34) written as 34/27; four ❌ rows that were three.
  • Behaviour asserted, never exercised — 3. Rail labels "wrapping" that fit one line; a header "wrapping" with 800 px of slack; a banner property called "forced" that was insurance.
  • Parity claimed, not checked — 2. M and N each claimed both languages carried a constraint that shipped in one; S10 shipped a whole screen with no Amharic while its note passed.

Two method changes came out of this and both are now standing: delivery notes are written after a claim-by-claim check of the file, adopted at Section N; and status hues are reserved to their semantic components, adopted at Section S. The lesson the batch paid most for: the first was never applied backwards, which is how S10 survived eleven sections. A method change is retroactive or it is decoration.
