## 1. Executive Summary

This document specifies how the platform is built, shipped, run, observed, secured at the infrastructure layer, backed up, and recovered. It defines the **environment matrix** (local, CI, staging with real Telegram/SMS integrations, production) and the **production topology**: stateless app containers (Octane) behind a load balancer, dedicated Horizon worker pools per queue family (with the isolation the series demands — a slow AI job never delays a Telegram send), Reverb nodes, the scheduler singleton, the SMPP sidecar(s), PostgreSQL primary + streaming replicas, Redis (persistence-tuned per use: cache vs queues vs routing state), object storage, ClamAV, and the CDN layer serving the widget and media. It specifies the **CI/CD pipeline** with every gate the series accumulated (isolation suite, RBAC route-mapping, adapter conformance, golden fixtures, the four-registry cross-check, string-lint + hostile-theme sweep, audit coverage harness, performance budgets), **blue-green deployment** with expand-contract migrations and flag-decoupled releases, **observability** (metrics, logs with the scrubber, traces via trace_id, dashboards, and the alert catalog every module registered), **SLOs and error budgets**, the **incident-management framework** (severities, the runbook index for every FS-scenario the series defined, the drill calendar), **backup and disaster recovery** (RPO ≤ 15 min / RTO ≤ 4 h, tested restores, the backup-generation metadata Doc 17’s erasure honesty reads), **secrets management**, **network architecture** (ingress allowlists for webhooks, egress proxy for Telegram/AI/SMS, no-internal-target rules), **email deliverability** per tenant sender (SPF/DKIM/DMARC automation and monitoring), the **vendor register** (AI providers, gateways, CDN — with exit criteria), capacity planning against the load profiles, and the compliance-infrastructure hooks (WORM anchor storage, per-market checklists). The stance: every guarantee made in Documents 01–17 is only as true as this document makes it operationally.

## 2. Purpose

- Turn the series’ budgets and degradation contracts into a concrete, costed, runnable topology with the operational discipline (gates, drills, runbooks) to keep them true.

- Define one deployment pipeline where a release physically cannot ship if any module’s contract tests fail.

- Make recovery boring: rehearsed restores, rehearsed failovers, rehearsed incident flows — before the first real one.

## 3. Scope

**In scope:** environments; production topology and sizing; container/build strategy; CI/CD stages and the gate inventory; migration discipline; deployment and rollback; configuration/secrets; networking (ingress/egress/DNS/TLS); CDN; observability stack, dashboards, alert catalog, SLOs; incident management, severities, runbook index, drill calendar; backups & DR incl. the erasure-honesty metadata; email deliverability infrastructure; the vendor register; capacity planning & scaling triggers; cost posture; compliance-infrastructure (anchors, per-market checklist). **Out of scope:** application code architecture (owning docs); test *content* (Doc 19 — this doc provides environments and load profiles); operator-side device guidance (Doc 05’s support-phone runbook page is referenced, authored there); billing/commercial infrastructure (not in product).

## 4. Functional Requirements

### 4.1 Environments

FR-01 Matrix: **local** (Docker Compose: full stack incl. MinIO, Mailpit, mock Telegram/SMS/AI providers, seeded tenant; parity rule — RLS, Octane, queues all on, per Doc 01 SEC-01); **CI** (ephemeral per-pipeline stack for integration/browser suites); **staging** (production topology at reduced scale, real integrations: the permanent staging bot + Business account on a dedicated device [Doc 05 Rec-1], a real Ethiopian gateway sandbox [Doc 14 Rec-2], AI providers on staging keys, the pseudo-locale tenant [Doc 16], the drill target); **production**. Promotion is strictly local → CI → staging → production; no environment skips. FR-02 Staging data policy: synthetic + the golden-fixture corpora only; production data never copies down (a hard rule with one audited exception path: a sanitized, approval-gated extract tool for bug reproduction that applies the Doc 08/17 masking rules — its use is a high-visibility audit event). FR-03 Region: primary region EU-central or Middle-East (Ethiopia RTT-optimized per the series decision), with the CDN edge handling widget/media latency; DR capability in a second region (§4.8).

### 4.2 Production topology

FR-04 Components (each independently scalable, each with a health endpoint): - **app** (Octane/FrankenPHP, stateless, N≥3): HTTP/API/Inertia + webhook ingress controllers. - **workers**: Horizon supervisors partitioned per the series’ queue families — telegram-in/out, webchat-in/out, media, ai (priority lanes per Doc 09 FR-03), sms (three lanes per Doc 14 NFR-02), automation, reports, outbox-relay, audit (per-tenant lanes per Doc 17 T-03) — with per-family container pools so saturation isolates (the platform’s repeated isolation promise made physical). - **reverb** (N≥2 behind the LB with pub/sub backplane), **scheduler** (singleton with leader election), **smpp-sidecar** (per bind, Doc 14 T-03, mTLS to app network), **clamav** daemons, **anchor-writer** (Doc 17 T-04’s external anchoring, isolated credentials). - **postgres**: primary + ≥1 streaming replica (sync or near-sync per RPO), PgBouncer; replicas serve heavy read paths flagged safe (reports aggregates, KB public reads) — never inbox read models (staleness contract there is Redis-based, not replica-based). - **redis**: two instances by durability class — redis-volatile (cache, presence, rate limits; allkeys-lru) and redis-durable (queues, outbox coordination, routing/timer ZSETs; AOF everysec) — the split prevents cache pressure evicting queue state (a classic failure the series’ rebuild patterns should never actually need). - **object storage** (S3-compatible, versioning on the audit/anchor buckets, lifecycle rules per retention), **CDN** (widget bundles per Doc 13 FR-04’s channels, media signed-URL passthrough, public KB cache per Doc 10 T-05). FR-05 Sizing v1 (L2-validated baselines, scaling triggers in §4.10): 3× app (4 vCPU/8 GB), worker pools totaling 8 vCPU dedicated with per-family minimums (telegram-out and sms never below 1 dedicated worker each), 2× reverb (2/4), Postgres 8 vCPU/32 GB + replica, Redis 2×(2/8), staging at ⅓.

### 4.3 Build & CI/CD

FR-06 Build: monorepo → deterministic Docker images (app image shared by app/workers/scheduler roles via command; sidecar and anchor-writer separate); SBOM generated per image; images signed; dependency scanning (composer/npm audit + container CVE scan) blocking on critical. FR-07 Pipeline stages (every push): lint+static (PHPStan, ESLint, the **string-lint** [Doc 16 FR-05], the **no-channel-conditionals grep** [Doc 04 T-09], migration-safety linter [§4.4]) → unit → integration (ephemeral stack): the accumulated **gate inventory**, all blocking: Doc 01 isolation suite + outbox chaos; Doc 02 enumeration/lockout/scrubber; Doc 03 route→permission mapping + precedence matrix; Doc 04 adapter conformance (fake adapter) + ordering fuzz; Doc 05/13 adapter fixture suites; Doc 06 transition matrix + invariant index; Doc 09 golden conversations + injection red-team (replay mode); Doc 10 publish atomicity; Doc 11 determinism harness; Doc 12 SLA property tests + dry-run parity; Doc 14 guard truth table + state machine; Doc 15 four-surface parity + exclusions; Doc 16 hostile-theme sweep + registry cross-checks (the four-registry constitution, Doc 17 NFR-06); Doc 17 coverage harness + immutability physics test → browser suites (Doc 07 shortcuts/states, widget hostile-host, a11y sweeps) → performance budgets (Lighthouse routes, loader timing, the L1 micro-bench) → staging deploy (auto) → staging smoke + the nightly-class suites on schedule (L2 soak, chaos drills, live-provider AI goldens per Doc 09 T-09) → production deploy (manual approval, two-person for migration-bearing releases). FR-08 The gate inventory is itself a registry (a fifth, meta one): each gate maps to its owning doc’s AC; removing or skipping a gate requires the same change control as the constitution registries — a release that “temporarily disables” a gate is the incident precursor this rule exists to prevent.

### 4.4 Migrations & deployment

FR-09 Migration discipline: **expand-contract** only (add-nullable/backfill/enforce in separate releases; drops two releases after deprecation); a migration-safety linter blocks: destructive ops in the same release as code depending on them, long-lock patterns (non-concurrent index creation on hot tables), audit-table changes without the Doc 17 FR-11 change-control flag; partition pre-creation jobs (Docs 01/04/17) verified in CI against future dates. FR-10 Deploy: blue-green for app/reverb/workers (green receives traffic after health + smoke; workers drain blue gracefully — in-flight jobs complete per Doc 16 FR-12’s pause semantics); scheduler leader hand-off; rollback = pointer flip (≤ 2 min) + the flag system for feature-level retreat (releases decoupled from exposure per Doc 01’s stance); widget rollout follows Doc 13 FR-04’s own staged channel independent of app deploys. FR-11 Release notes are generated from the gate inventory + migration list + flag changes — the deploy record an incident review can trust.

### 4.5 Networking & security infrastructure

FR-12 Ingress: LB with TLS 1.2+ (managed certs, HSTS per Doc 02 T-07), WAF baseline rules; webhook paths (/hooks/telegram/*, /hooks/sms-dlr/*) rate-limited per key at the edge and allowlist-annotated (Telegram’s published ranges monitored, alert-on-drift rather than hard-block — availability over brittle IP pinning, documented trade-off); admin/staff app optionally IP-restricted per tenant (Doc 02 SEC-05’s infrastructure half). FR-13 Egress: all outbound third-party traffic through the egress proxy with per-destination allowlists (api.telegram.org, AI provider endpoints, gateway endpoints, anchor endpoint, breach-check API) — the SSRF posture (Docs 04/12) is a network property here, not only code; internal networks unreachable as webhook/rule targets by proxy policy. FR-14 Secrets: vault (or sealed cloud secret manager) with per-service identities; rotation runbooks per secret class (bot tokens via Doc 05 flows, gateway creds via Doc 14, DB/Redis creds with rolling restarts, signing keys with dual-validity windows); the log scrubber (Doc 02 SEC-08) runs as a Loki pipeline stage *and* in-app — two layers; quarterly secret-inventory review on the drill calendar. FR-15 Email deliverability: per-tenant sender domains provisioned with automated SPF/DKIM (platform-managed selectors)/DMARC guidance; verification status exposed to Doc 16 SEC-03; outbound mail via a reputable relay with per-tenant sub-identities; bounce/complaint webhooks feed sender health (Doc 16 EC-11’s lapse detection); DMARC reports monitored platform-side.

Alert changes go through the gate-registry change control (FR-08) — silence is never informal. FR-19 Synthetics: staging+prod probes — login flow, webhook round-trip (staging bot self-message), widget load from 3 geographies incl. Addis-representative, send-an-SMS-to-testnumber (staging), report render; probe failures alert per catalog. FR-20 SLOs (per NFR sources) & error budgets: API availability 99.9%; inbound message pipeline p95 ≤ 1.5 s (Doc 04); outbound send p95 ≤ 2 s in-shape; realtime delivery ≤ 2 s (Docs 07/15); webhook ACK p99 ≤ 250 ms; error-budget policy: budget exhaustion freezes feature deploys (gate) until burn-rate recovers — reliability spends before features do.

### 4.7 Incident management

FR-21 Severities: **Sev-1** (customer-data integrity, cross-tenant exposure, audit tamper signal, platform down) — page immediately, incident commander, comms cadence 30 min; **Sev-2** (a channel down, AI injection-class discovery [Doc 09 SEC-03], SLA-affecting degradation) — page in-hours/on-call after; **Sev-3** (degraded non-critical, single-tenant issues) — ticketed. Every FS-scenario in Docs 01–17 maps to a runbook in the index (FR-22) with its severity pre-assigned. FR-22 Runbook index (the series’ FS sections operationalized; each runbook: detection, first fork, actions, verification, comms template): Redis loss (per instance class), outbox/consumer lag, RLS-failure emergency read-only, Telegram outage + window-sweep pause (Doc 05 FS-01), webhook silent-break re-registration, provider failover/exhaustion ladders (Doc 09 FS-01), retrieval-index rebuild, routing-state rebuild, SMS country-outage ladder (Doc 14 EC-12), gateway credential expiry, projector/aggregate rebuilds, theme-cache fallback, flag-store fail-static, audit consumer lag + verify-mismatch fork (EC-12 Doc 17), DLQ re-drive, partition-maintenance failure, backup-restore, region failover, **and the incident page** (Doc 16 AC-10) as the universal first tab. FR-23 Drill calendar (staging, scheduled, results logged): monthly — node-kill replay (Doc 04 SS-04), restore-from-backup with timing; quarterly — region-failover tabletop→live-alternate-year, Telegram business-connection revocation walk (Doc 05 AC-03 rerun), SMS failover (Doc 14 SS-03), erasure walkthrough (Doc 17 Rec-3), secret-inventory review; per-release-window — the L2 soak. Drill results feed the reliability review; a missed drill is itself a tracked deviation. FR-24 Post-incident: blameless review within 5 working days, actions tracked to closure, the Doc 17 trace/audit forensics as the factual backbone (SS-02’s pattern institutionalized).

### 4.8 Backup & disaster recovery

FR-25 Backups: Postgres — WAL archiving (RPO ≤ 15 min) + nightly base backups, 35-day PITR window, monthly archival snapshots per retention policy; redis-durable — AOF + hourly RDB snapshots (queues are recoverable-by-design via outbox/DB truth, so Redis backup is acceleration, not correctness — stated so restores prioritize right); object storage — versioning + cross-region replication for the audit/anchor/brand buckets, lifecycle for media per retention; configuration — the Doc 16 export bundles snapshotted per release. FR-26 **Backup-generation metadata** (Doc 17’s honesty dependency): every backup generation registered {id, created_at, expires_at, scope}; the erasure engine computes “fully expired by” from it (Doc 17 T-05); backup deletion jobs honor legal holds (the one case backups are pruned early is never — holds extend, they don’t shorten). FR-27 Restore verification: the monthly drill restores the latest backup to an isolated stack and runs the golden-fixture smoke + row-count reconciliation; an unverified backup is treated as no backup (the drill IS the backup system). FR-28 DR: RPO ≤ 15 min / RTO ≤ 4 h documented and drilled; second-region standby (replicated storage + infra-as-code re-provision; warm DB replica optional cost tier); DNS cutover runbook; the widget CDN and status page live outside the primary region’s failure domain; a public status page (platform-branded, per-tenant views optional §19) is the comms surface.

### 4.9 Vendors & compliance infrastructure

FR-29 Vendor register (Doc 09 Rec-5 generalized): AI providers, SMS gateways/aggregators, CDN, email relay, anchor/timestamp service, GeoIP — each with: data-processing terms pinned, data sent (minimization statement), exit criteria + tested alternative (the AI fallback chain and gateway failover are the *practiced* exits), review cadence (quarterly), incident contacts. The register is a living doc referenced by Sev comms. FR-30 Per-market compliance checklist (Doc 14 R-04’s referenced artifact): before enabling a new country route/tenant market — sender-ID rules, opt-out mandates, quiet-hour laws, data-residency flags, gambling-communications restrictions — checklist completion recorded (audited) before the routing row activates. FR-31 WORM/anchor storage: object-lock bucket (compliance mode) for Doc 17 day-seals and export manifests where the tenant enables anchoring; the anchor-writer’s credentials are write-only (Doc 17 SEC-05) and isolated from all other service identities.

### 4.10 Capacity & scaling

FR-32 Load profiles (Doc 19’s shared definitions): **L1** micro-bench (budget verification), **L2** target scale (the series’ repeated envelope: 200 msg/s inbound, 500 agents, 10k widget sessions, 50 msg/s/endpoint bursts, 500 events/s), **L3** 3× headroom (burst survival, degraded-but-honest acceptance). FR-33 Scaling triggers (alert→action pairs): queue-family lag SLO burn → scale that family’s pool (auto within bounds, per-family max caps protect DB); app p95 burn → add app nodes; Reverb connection ceiling 80% → add node; Postgres: replica lag / connection saturation → PgBouncer tuning then vertical; Redis memory 70% on durable → immediate review (never wait for eviction); storage growth vs the Doc 04 NFR-06 budget → lifecycle review. Kubernetes-readiness: the Compose topology maps 1:1 to a Helm chart kept in-repo from day one (the migration is a scheduling change, not a rearchitecture).

## 5. Non-functional Requirements

NFR-01 Deploy lead time (merge→production, gates green) ≤ 1 day; rollback ≤ 2 min (FR-10); deploy frequency supported: daily. NFR-02 The full CI gate inventory ≤ 40 min wall-clock (parallelized); the nightly class ≤ 4 h. NFR-03 Observability freshness: metric scrape ≤ 15 s; alert firing ≤ 1 min from condition; dashboard-as-code drift = 0 (provisioning is the source). NFR-04 Restore drill: full restore + verification ≤ 3 h (inside the RTO with margin). NFR-05 Patch cadence: critical CVEs ≤ 72 h (the image pipeline supports rebuild-and-roll same-day); routine monthly. NFR-06 Infrastructure-as-code coverage 100% (no console-crafted resources; drift detection weekly).

## 6. User Stories

US-01 As a platform engineer, I merge a change and the pipeline tells me — before any human review — whether I broke tenancy, permissions, ordering, audit coverage, or a golden conversation. US-02 As the on-call, every alert links a runbook whose first fork I’ve rehearsed in a drill this quarter. US-03 As the platform owner, when Telegram wobbles at midnight, the system queues honestly, the right people are paged at the right severity, and the morning report writes itself from events and deploy markers. US-04 As a compliance officer, “fully expired by” dates in erasure reports come from real backup metadata, and the restore drills prove the backups those dates describe actually work. US-05 As a developer, staging is real enough (real bot, real gateway sandbox, pseudo-locale tenant) that “works on staging” means something. US-06 As the business, reliability spends its budget before features do — and I can see the budget.

## 7. Business Rules

BR-01 Gates are constitutional (FR-08): no release ships around a red gate; the escape hatch is fixing or formally changing the gate, never skipping it. BR-02 An unverified backup is no backup (FR-27); an unrehearsed runbook is a hypothesis (FR-23) — verification and drills are the product, not overhead. BR-03 Parity or it didn’t happen: local and CI run the same isolation-relevant configuration as production (Doc 01 SEC-01’s rule owned here); “it only fails in prod” bugs get a parity-gap review, not just a fix. BR-04 Honest degradation over silent failure — the series’ repeated contract — is enforced here by the alert catalog: every degraded mode a document specified has a metric and an alert, or the degradation contract is unshipped. BR-05 Error budgets govern (FR-20): exhaustion freezes features automatically; overriding the freeze is a platform-owner decision, logged. BR-06 Production data stays in production (FR-02); the sanitized-extract exception is audited, approval-gated, and rare by design. BR-07 The two-Redis split (FR-04) is permanent: durable state and evictable cache never share an instance, whatever the cost pressure.

## 11. Security Requirements

SEC-01 Network segmentation: DB/Redis/sidecars on private networks; only app/workers reach them; the anchor-writer reaches only the anchor endpoint; admin surfaces optionally IP-gated per tenant. SEC-02 Least-privilege service identities per component (the app role’s audit-table grants per Doc 17 FR-11 are provisioned here and asserted per deploy by the physics test). SEC-03 Image supply chain: signed images, SBOM retention, base-image update cadence, CVE gates (FR-06); build runners isolated from production credentials (deploy credentials only in the deploy stage’s environment). SEC-04 The egress proxy’s fault-injection capability (T-04) is staging-only by credential separation — production proxy config is immutable-per-release. SEC-05 Backup encryption at rest with keys separate from primary-data keys; restore drills include key-availability verification (a backup you can’t decrypt is FR-27’s “no backup”). SEC-06 Pen-testing cadence: external test annually + after major auth/tenancy changes; findings tracked with the incident-action machinery; the Doc 19 red-team fixtures (injection, enumeration, scope) run continuously as the internal floor. SEC-07 Access to production: SSO + hardware-key MFA for infrastructure consoles, session-recorded break-glass with dual authorization, all access logged into the platform’s own monitoring (the infrastructure watches itself with the same posture Doc 17 gave the application).

## 12. Performance Requirements

- The L2 envelope validated on the FR-05 sizing before launch and re-validated per quarter or per ±30% traffic change; L3 burst drill semi-annual.

- Per-component budgets: LB+app overhead ≤ 10 ms p95 over application time; PgBouncer ≤ 1 ms; egress proxy ≤ 5 ms p95; scrubber pipeline ≤ 2 s log-availability lag.

- Cost posture: monthly infrastructure review against a per-1k-conversations unit cost; the two-Redis and replica decisions carry documented cost justifications (reliability line items, not surprises).

## 13. Accessibility Requirements

Internal surfaces meet the platform’s baseline: the status page fully WCAG 2.2 AA (it is public and read during stress — plain language, no color-only states); Grafana dashboards use color-blind-safe palettes with threshold annotations as text; runbooks in accessible markdown (headings, lists, no ASCII-art-only critical steps — diagrams paired with text procedures).

## 14. Localization Requirements

The status page supports en + am (incident comms templates pre-translated for the common scenarios — a Telegram-outage notice in Amharic is written *now*, not at 2 AM); internal tooling remains en; timestamps on all ops surfaces UTC-first with local-time hover (the inverse of product surfaces, correctness over comfort); the per-market checklist (FR-30) localizes per jurisdiction as it grows.

## 15. Edge Cases

EC-01 Deploy during a Telegram burst → blue-green + worker drain means in-flight processing completes; the lane FIFO (Doc 04) tolerates the worker handover; validated by deploying during the L2 soak (a standing pipeline test, not a hope). EC-02 Scheduler leader dies mid-sweep → leader election + idempotent sweeps (every sweep in the series is re-runnable by design); the gap is bounded by election time (≤ 30 s). EC-03 Replica promoted with lag (failover during writes) → the RPO window applies; the outbox/event architecture makes the loss surface enumerable (unrelayed outbox rows on the lost primary) — the failover runbook includes the reconciliation query and the honest-comms template for the bounded loss. EC-04 Redis-durable failover loses seconds of AOF → queues/timers rebuild from DB truth per every module’s FS pattern; the drill verifies rebuild ≤ its budgets; volatile loss is a non-event by design. EC-05 CDN regional degradation affecting Addis specifically → the geo synthetic (FR-19) catches it; the runbook’s fork includes origin-serve fallback for the widget shim (slower, alive). EC-06 A gate flakes (intermittent browser-suite failure) → quarantine protocol: the gate stays blocking, the flaky *test* moves to a quarantine lane with a 2-week fix SLA and owner — gates never get “known-flaky, ignore” status (BR-01’s corollary). EC-07 Clock drift on a node (Doc 02 EC-07’s infrastructure half) → NTP monitoring, >5 s alert, node cordon at >30 s (TOTP and seal-ordering protection). EC-08 Object-storage regional replication lag vs an erasure’s “fully expired by” → the metadata (T-07) tracks per-region generations; the honest date is the max across regions. EC-09 Two migration-bearing releases queued same day → the pipeline serializes them (expand-contract makes ordering safe, serialization makes it simple); the two-person approval sees both. EC-10 Vendor sunset (an AI provider deprecates a model) → the register’s exit criteria + the model-per-task abstraction make it a config change rehearsed by the failover drills; the review cadence exists to see it coming.

## 16. Failure Scenarios

(The module-level FS-catalog lives in Docs 01–17 and the runbook index; these are the infrastructure-level composites.) FS-01 **Primary DB loss** → replica promotion (runbook, drilled): RPO window applies, EC-03 reconciliation, app reconnect via PgBouncer, full-stack smoke, comms per template; target inside RTO with the monthly-restore muscle memory as backstop if promotion fails. FS-02 **Region outage** → DR runbook: DNS cutover, storage-replica promotion, infra re-provision from IaC, the status page (out-of-region) carries comms; RTO ≤ 4 h drilled at tabletop + alternate-year live. FS-03 **Observability outage** (Prometheus/Loki down) → the platform runs blind-but-fine; the meta-monitor (a tiny external probe on the monitoring itself) pages; restoring sight is Sev-2 with a strict clock (blind operation > 1 h auto-escalates). FS-04 **CI unavailable** → deploys pause (BR-01 — no gate, no ship); a documented emergency-hotfix path exists requiring platform-owner + the full gate run retroactively within 24 h (the one sanctioned deviation, heavily logged). FS-05 **Cascading queue backlog** (a poison-pattern across families) → the DLQ + per-family isolation contain; the composite runbook sequences: park poison (Doc 04 FS-05), scale consumers, verify budgets family-by-family; the L3 drill rehearses exactly this shape.
