# ADR 0006 — GeoIP: `maxmind-db/reader` dependency and a checked-in synthetic stub `.mmdb`

**Status:** accepted
**Date:** 2026-08-02
**Owner trigger:** Doc 02 step 6 close-out (FR-12 devices screen, T-08 GeoIP, FS-04 degradation)

## Context

Doc 02 T-08 requires GeoIP city resolution for the devices screen with three
constraints: **local MMDB file, weekly refresh, in-process lookups only** — no
external API on the login path, ever. NFR-04 requires GeoIP to be a fail-open
enrichment with a named metric; FS-04 requires that a corrupt database degrade
to "location unavailable" rather than break the page. The devices migration
(2026_07_31_010400) already fixed the design point that the city is resolved at
login and **stored** on the device row, so a bad database never fails a render.

Two problems needed a ruling:

1. **Reading MMDB needs code we do not have.** The MMDB binary format (search
   tree + data section + metadata) is not something to hand-parse casually on an
   auth path.
2. **Tests need a database we can check in.** CLAUDE.md §8 forbids production
   data in fixtures, and MaxMind's real GeoLite2 databases are large,
   redistribution-encumbered, and non-synthetic. CI must not download anything
   (the egress rules), so the fixture has to live in the repo.

## Decision

1. **New dependency: `maxmind-db/reader` (^1.13).** MaxMind's official pure-PHP
   MMDB reader — no extension requirement, no service, no egress. It is used by
   `App\Support\GeoIp\GeoIpResolver` only; nothing else may touch the file
   format.
2. **A checked-in synthetic stub database:** `fixtures/geoip/stub-city.mmdb`,
   generated by the also-checked-in `fixtures/geoip/generate-stub.php` — a
   deliberately minimal MMDB **writer** (ip_version 4, record size 32) with a
   fixed `build_epoch`, so regeneration is byte-deterministic. The stub maps
   only RFC 5737 documentation ranges (TEST-NET-1/2/3), which can never be real
   client addresses — the fixture is self-identifying, in the same spirit as
   `+251-90000xxxx` phone numbers:

   | Network | City (en) | City (am) | Country |
   |---|---|---|---|
   | 192.0.2.0/24 | Addis Ababa | አዲስ አበባ | ET |
   | 198.51.100.0/24 | Dire Dawa | ድሬዳዋ | ET |
   | 203.0.113.0/24 | — (country only) | — | ET |

   The third network deliberately has no city, so the "resolves but has no city
   name" shape is testable, distinct from FS-04's "database corrupt" shape.

3. **The stub is verified by the official reader, not by our own code.** The
   fixture's test opens it with `MaxMind\Db\Reader` and asserts the exact
   records above. Writer and reader come from different authors, so a shared
   misunderstanding of the format is structurally unlikely: if the official
   reader returns our records, the file is a valid MMDB.

4. **Production data is Doc 18's.** The real GeoLite2-City file and its weekly
   refresh (T-08) are delivery infrastructure, owned by Doc 18 alongside the
   other operational material. `GEOIP_DATABASE_PATH` names the file; when it is
   unset, empty, missing or corrupt the resolver returns null with the named
   metric `auth.geoip.lookup_failed` and device rows store IP only (FS-04).

## Consequences

- Local and CI test runs resolve TEST-NET addresses to the fixture cities with
  both `en` and `am` names, which also exercises §14's "place names localized
  where data allows" without any real-world data.
- The generator is ~200 lines of format-writing code that exists ONLY for the
  fixture. It is not a general MMDB writer, must never run in production, and
  refuses sizes its minimal encoder cannot express rather than guessing.
- Anyone regenerating the stub must commit generator and fixture together; the
  fixture test fails loudly if they drift.
